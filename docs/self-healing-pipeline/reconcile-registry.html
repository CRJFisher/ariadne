Reconciling the Classifier Registry

The classifier registry is a human-owned write surface, like backlog/. reconcile-registry is its decision skill over one fenced writer — the registry's analogue of prioritize over export_to_backlog.ts. It detects work the rest of the pipeline has already done, previews the mechanical flips, and applies them through a single atomic_update_registry transaction. The human stays the sole decider; the skill makes each decision cheap.

The pipeline has three human-owned write surfaces. Each pairs a deliberate decision step with exactly one fenced writer:

The skill owns no logic of its own. All work runs through one script, .claude/skills/triage/scripts/reconcile_registry.ts — the registry's only human-invoked writer, reaching the registry only through atomic_update_registry(path, mutator), one lock-fenced read-mutate-write per invocation. The skill is disable-model-invocation: true: the model never self-invokes it, and the script never runs on the autonomous sweep.

Three signals, three writes

The script scans the mechanically-detectable signals and proposes the corresponding registry write. It never authors rule prose and never makes the permanent judgment — those stay human creative and judgment work.

#Signal (mechanically detected)Proposed registry write
1 A fix-bearing git log scope in this repo matches a wip rule's backlog_task. Only fix and feat commits count — a docs(198) or review(198) commit references the task without fixing anything. The match is exact-id, never prefix (190.22 does not match 190.22.21); range scopes like 190.17.12-14 expand to their exact ids via the shared grammar in scripts/check-commit-message.ts. wip → fixed, citing the newest matching commit subject as the audit line
2 Each project's latest finalized triage_results/<run-id>.json names a rule in classifier_regressions[] — the published rule_id field carries the registry rule's group_id. Set drift_detected: true; append the missing drift_evidence[] rows, append-only and deduped by entry_index, so a re-run after apply proposes nothing
3 The human elects to promote a rule (--id <group_id> --promote). Flip to permanent, then regenerate core's bundled slice via generate_permanent_data.ts

Malformed or stale published files are reported in skipped_sources and skipped — never fatal. No commit hash is stored; the backlog_task link plus the git log are the entire audit trail.

Preview → narrow → apply

A --dry-run scans every signal and prints the proposed changeset writing nothing; selectors narrow the set; dropping --dry-run applies through atomic_update_registry — one lock-fenced read-mutate-write per invocation. Proposals re-fold onto the locked read, so a proposal computed from a stale preview degrades to a no-op instead of clobbering a concurrent edit.

Which lifecycle arrows carry a detector

The lifecycle diagram shows every transition as a human edit, and that holds: the human remains the decider on every arrow. Two arrows carry a detector — the signal is found mechanically and proposed — and one carries a mechanical apply-step, the regeneration the lifecycle describes. The human confirms each.

Selectors

FlagSelects
--dry-runPrint the proposed changeset, write nothing. Always the first run.
--fixedwip → fixed proposals only.
--driftDrift-flag proposals only.
--id <group_id>Exact rules (repeatable). Overrides --fixed/--drift: both signals are scanned, and only the named rules' proposals survive. Ids matching no proposal report in missing_ids.
--id <group_id> --promoteNames rules directly, bypassing detection: flip them to permanent and sync the slice. Cannot combine with --fixed/--drift — promotion is its own transaction.

--id has two modes. As a selector it overrides the signal filters and narrows the detected proposals to the named rules; with --promote it bypasses detection entirely and names the rules to flip. With no selectors, every proposal across both detection signals is selected.

The JSON summary

The script's only stdout is one JSON summary:

FieldMeaning
proposalsThe changeset, grouped by transition (wip_to_fixed, drift_detected, promote_to_permanent).
appliedA registry write happened. false under --dry-run, when nothing was proposed, and when the fold was byte-identical to the current registry (an idempotent re-run).
permanent_slice_changedCore's permanent_data.ts differs from a fresh render — rewritten on a real --promote, reported-only under --dry-run (rendered from the would-be-promoted rules).
missing_ids--id values matching no proposal (selector mode) or no rule (--promote mode).
rejected_promotions--promote targets refused, with the reason (classifier.kind is "none", or already permanent).
drift_unknown_rule_idsPublished rule_ids with no registry rule — review signals, never writes.
skipped_sourcesPublished files that failed to read or parse — reported, never fatal.

Each wip_to_fixed proposal carries matched_subject (the newest matching commit) as its audit line; each drift_detected proposal carries flagged_by, the {project, run_id} provenance of every run that flagged the rule.

Promotion is guarded. A rule whose classifier.kind is "none" is refused — core's validate_permanent_slice cannot load an unclassified permanent rule, so the slice generator filters on status === "permanent" and classifier.kind !== "none". A rule already permanent is refused too. Both refusals exit zero and report in rejected_promotions.

Two structural guards

Two whole-repo invariant tests enforce the surface — the bundled slice cannot drift from the registry, and only the fenced writer can serialize it:

permanent_data.sync.test.ts

Asserts the committed packages/core/src/classify_entry_points/permanent_data.ts byte-equals the slice freshly rendered from the source registry, through the shared render_permanent_slice_module in @ariadnejs/types — the same function the generator writes through. A hand-edit to either file fails the test; the fix is to edit the registry and re-run generate_permanent_data.ts.

registry_writers.test.ts

The AST walk in packages/skill-fs/src/registry_writers.test.ts flags any raw write primitive against a registry-shaped path, and any call to serialize_known_issues_registry_json outside an allowlisted file. reconcile_registry.ts is the one entry in ALLOWED_SERIALIZER_CALLERS; its only serializer call sits strictly inside the atomic_update_registry mutator closure.

The human is the sole decider. The skill proposes; the human confirms every flip. The skill is disable-model-invocation: true and the script never runs on the autonomous sweep — the model never writes the registry.
