Triage is the sensing link of the loop: a self-contained per-commit run that detects entry-point candidates, spends LLM budget only on the unexplained residual, and publishes every verdict as one schema-v5 artifact.

Triage: Sensing False Positives

skill: triage per-commit run registry: read-only output: triage_results/<run-id>.json (v5)

The four phases

PhaseScript / agentDoes
1 · Detect scripts/detect_entrypoints.ts Calls @ariadnejs/core (load_project → trace_call_graph) to produce the raw entry-point candidate set. Output: analysis_output/<project>/detect_entrypoints/<ts>.json. One detection feeds many triage runs.
2 · Prepare scripts/prepare_triage.ts Captures target HEAD, builds run-id <short-commit>-<iso-ts>, classifies every candidate via core's enrich_call_graph against the lifecycle-filtered registry, applies the TP cache, partitions into three buckets, and writes the run directory.
3 · Loop triage-investigator (Sonnet, worker pool N=5) Investigates each residual entry; every agent writes one self-contained TriageVerdict to results/<entry_index>.json. Entries stay pending until a verdict file lands, so crash recovery is automatic.
4 · Finalize scripts/finalize_triage.ts Builds the published v5 triage_results/<run-id>.json entirely from the per-entry verdict files plus triage.json, atomically writes it, seals the manifest (status: "finalized"), and clears LATEST.

The three buckets

Prepare hands every detected candidate to core's enrich_call_graph with the lifecycle-filtered registry, then partitions the result. build_triage_entries assigns entry_index by concatenation order: auto-classified first, then residual.

auto-classified

A predicate or builtin classifier from the registry matched at or above its min_confidence. The entry is created with route: "known-unreachable", status: "completed", and known_source: "registry:<group_id>" — a verdict exists before the Loop starts.

TP-cache reuse

A prior finalized run at the same commit confirmed this exact entry as true dead code. The entry flips to route: "known-unreachable", status: "completed", with known_source: "previously-confirmed-tp" and a tp_source_run_id recording provenance.

residual

No classifier matched and no cached verdict exists. The entry is route: "llm-triage", status: "pending", carrying any sub-threshold classifier_hints into the investigator prompt. Ordered by tree_size descending (then file + line for a total order) and capped at --max-count (default 150).

Why the first two buckets are never investigated. An investigator exists to answer one question: is this candidate genuinely unreachable, or did the resolver miss a caller? For an auto-classified entry that question is already answered deterministically — a registry rule encodes a known root cause, so re-asking an LLM buys nothing and costs a full investigation. For a TP-cache entry the question was already answered by a real LLM investigation at the identical commit, so the answer cannot have changed. LLM budget is spent exclusively on the residual — the only entries whose status is actually unknown.

The --max-count cap applies only to the residual; auto-classified entries are always kept in full and never count toward it. Largest call trees go first because a large unreachable tree is the candidate most likely to matter, and the deterministic tiebreak means two runs over the same analysis JSON pick the same top-N.

The registry as a read-only filter

Prepare loads the full registry (known_issues/registry.json, permanent + wip rules) and passes it through active_rules_for_classification before classification. Two rule classes are dropped:

Dropped ruleWhy it must not fire
status: "fixed" The underlying Ariadne bug is resolved. A fixed rule that keeps firing would silently suppress entries that the now-correct code path handles — the loop would never confirm its own healing.
status: "wip" with drift_detected: true Review flagged the classifier as mis-matching. Leaving it live would auto-suppress exactly the entries that are queued for re-examination.
Write boundary. Triage reads the registry as a classification filter and never writes it. Every status transition (wip, permanent, fixed, drift flags) is a human edit through atomic_update_registry — see Registry and Write Boundaries.

The TP cache: cross-run cost amortization

Re-running triage at the same target commit must not re-pay for verdicts that cannot have changed. derive_tp_cache (in finalize/confirmed_unreachable_reuse.ts) builds a reuse map from prior published results; apply_tp_cache_to_entries flips matching residual entries to completed before the Loop ever sees them.

The same-commit validity gate

The cache is gated entirely by the run-id's <short-commit>- prefix. all_finalized_runs_at_commit enumerates only finalized runs whose run-id starts with the current HEAD's short commit:

  • Same prefix → prior llm-tp verdicts are reused; only the new residual re-investigates.
  • Any new commit → the prefix differs, the cache misses entirely, and every entry re-investigates.
  • Non-git target (nogit-… run-ids) → caching is disabled.

Eligibility: only real LLM verdicts seed the cache

Only published confirmed_unreachable rows with source.kind === "llm-tp" are indexed:

source.kindCache-eligible?Reason
llm-tp Yes A real LLM investigation confirmed the entry unreachable at this commit.
registry:<group_id> No Excluded so the cache cannot outlive a rule deactivation — when a rule is marked fixed or its drift is detected, its entries return to the residual pool instead of being resurrected from cache.
previously-confirmed-tp No The published schema carries no origin chain, so a cache-hit row cannot prove its verdict traces back to a real investigation. A cache hit is never itself reused.

The cache accumulates across all finalized runs at the commit, scanned newest-first with newer runs winning on key collision. A run containing only previously-confirmed-tp rows contributes nothing, but does not block older runs' llm-tp entries from being included — so verdicts investigated in any earlier same-commit run stay reusable. The match key is (name, file_path, kind, start_line) with file_path relative to project_path (portable across machines), joined with NUL separators so no real identifier or path can collide. Registry-classified entries are never overridden by a cache hit — newer registry information wins.

Controls and known leaks

ControlEffect
--no-reuse-tpDisables the cache for this run; every residual entry re-investigates.
--tp-source-run <run-id>Pins a specific source run. The script throws if the pinned run-id is not at the current commit or its published file is missing — reuse across commits is refused.
Two accepted leaks. HEAD is the only validity signal: uncommitted target-repo edits do not bust the cache (commit first, or pass --no-reuse-tp), and Ariadne core changes do not bust it either (after tightening call resolution, run once with --no-reuse-tp to validate that prior TPs still hold).

Per-run state layout

Every invocation produces a self-contained run under ~/.ariadne/triage-entrypoints/triage_state/<project>/runs/<run-id>/. The project name is the isolation boundary — different projects run in parallel against the same state tree.

Path (relative to ~/.ariadne/triage-entrypoints/)Holds
triage_state/<p>/runs/<run-id>/manifest.json Run metadata: status (active / finalized / abandoned), full commit_hash, source analysis path, max_count, and the tp_cache record (enabled, source_run_id, skipped_count, skipped_entry_keys).
triage_state/<p>/runs/<run-id>/triage.json The TriageState: phase plus the full TriageEntry[] with per-entry route, status, and results.
triage_state/<p>/runs/<run-id>/results/<entry_index>.json Per-entry investigator verdict files — one strict TriageVerdict each. The single source of truth Finalize folds from.
triage_state/<p>/LATEST Pointer to the active run-id. Written by Prepare, cleared by Finalize (or abandon_run.ts); absent when no run is in progress. Phase 3–4 scripts default to it.
analysis_output/<p>/triage_results/<run-id>.json The published v5 artifact: novel_issues, classifier_regressions, confirmed_unreachable, uncertain. Kept forever — it is the permanent TP-cache source and the input to plan and diff_runs; run dirs may be pruned, this file may not.

Write ordering is deliberate at both ends of the run. Prepare writes manifest.json before triage.json and stamps LATEST last, so a concurrent prune_runs always sees the tp_cache.source_run_id protection signal as soon as the run dir exists. Finalize atomically writes the published artifact, seals the manifest, and only then clears LATEST — a crash between the two leaves the run discoverable as active. A manifest already marked finalized makes Finalize refuse outright rather than overwrite the published artifact.

What Finalize folds where

SourcePublished as
Verdict kind: "fp-novel"One novel_issues[] row per verdict, enriched with the entry's deterministic diagnosis / resolution_failure / receiver_kind.
Verdict kind: "fp-classifier-regression"Rolled up into classifier_regressions[] by should_have_matched_rule_id.
Verdict kind: "tp" + auto-classified + TP-cache entriesconfirmed_unreachable[] rows tagged source: "llm-tp" / "registry:<group_id>" / "previously-confirmed-tp", each carrying the cache match key (name, relative file_path, kind, start_line).
Verdict kind: "uncertain"One uncertain[] row with the verdict's reason and evidence.

Malformed verdict files halt Finalize with an explicit error — parse_triage_verdict re-parses every file, and there is no in-run consolidation: each false-positive verdict ships raw and self-contained, leaving offline grouping to plan.
