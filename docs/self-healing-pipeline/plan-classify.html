Plan is the classify link of the loop: an offline three-pass engine that turns published triage false-positives into reconciled, deduplicated engineering proposals — without ever touching the backlog, the registry, or core.

Plan: Grouping, Strategizing, Reconciling

skill: plan Pass A — group (deterministic) Pass B — strategize (opus) Pass C — reconcile (deterministic) planning-only

The engine reads completed triage runs — analysis_output/<project>/triage_results/<run-id>.json (schema v5) — and writes only its own task-DB under ~/.ariadne/plan/. The two deterministic passes (A and C) bracket a single judgement pass (B), so every LLM decision is validated structurally before it can reach durable state.

Pass A — Group: deterministic fault-area bucketing

group_runs.ts flattens every published false-positive (novel_issues[]) across the scanned runs into PlanTaskEvidence rows and buckets them by AriadneFaultArea. The pure core is group_fault_areas.ts — no I/O, no clock, no randomness; the entry script does the reading and persisting.

NovelIssue → PlanTaskEvidence

novel_issue_to_evidence carries each issue's provenance (member_evidence, member_symbol, project, run_id) plus exactly the inputs of derive_fault_area, kept verbatim: diagnosis, resolution_failure (normalized null-not-absent), and the disambiguator boolean has_uncaptured_indexed_grep_hit. Storing the raw fault signals — never a derived area — is what keeps the area recomputable on read against the current taxonomy.

The override chain

Before a member lands in its derived bucket, Pass A consults the membership-override store (~/.ariadne/plan/membership_overrides.json, written by prior reconcile passes) via follow_override_chain. Starting from the derived area, it looks up an override keyed on (area, member identity) and:

Chain outcomeConditionEffect
LandNo override exists at the current areaMember buckets at that area
Re-routeOverride names a suggested_areaMove there, then check the destination for its own override and follow again
SuppressOverride has suggested_area: nullMember is dropped from the sweep
Suppress (cycle)The chain revisits an areaEvery area in the cycle has already excluded the member — dropped

A member a strategist already judged mis-routed is therefore corrected here, deterministically, instead of being re-adjudicated every sweep. Two details keep re-routed members honest: needs_judgement and the escape-hatch description describe the member's derived area, so both are applied only when the member lands where it was derived (area === location.area) — an override-settled placement contributes neither.

Bucket output

Each FaultAreaBucket carries its evidence verbatim plus rollups: observed_count, sorted projects and source_runs, sorted descriptions (free-text signal, populated for the other escape hatch), and a needs_judgement flag. Buckets sort by observed_count descending, ties broken lexically by fault_area, so the strategist wave and every test assertion are deterministic. Buckets stage under ~/.ariadne/plan/staging/<sweep>/buckets/ alongside a manifest.json recording the full scanned scope — projects and run ids including zero-FP runs, which Pass C's orphan retirement depends on.

Pass B — Strategize: one opus strategist per bucket

The skill dispatches one plan-strategist sub-agent (opus, 200-turn) per bucket, capped at MAX_CONCURRENT_STRATEGISTS = 5 and drained in waves. The strategist hydrates its bucket with get_bucket_context.ts, plans, and writes one file — a StrategistPlan JSON (schema v1) under staging/<sweep_id>/plans/<fault_area>.json — returning nothing inline. It never writes code, the registry, or the backlog; its only write grant is ~/.ariadne/plan/staging/**.

Membership review first

Pass A's deterministic lookup can mis-route a member into a bucket whose bulk root cause it does not share — a borderline (stage, reason), a defaulted derivation, or a genuinely cross-area fault. The strategist is the one stage with judgement and code access, so before planning it emits a membership array: one verdict per evidence index, prioritizing the needs_judgement_indices (members whose derivation defaulted, the likeliest mis-routes).

{ "index": 0, "belongs": true,  "reason": "" }
{ "index": 3, "belongs": false, "reason": "this is an import miss, not a name-resolution one",
  "suggested_area": "import_resolution" }

The review must be total (one verdict per index, no gaps) and consistent (no node may ground an excluded index) — both enforced by the validator. Tasks are planned over the members that belong; an excluded member grounds nothing.

The StrategistPlan tier tree

The core_fix_effort cost axis

Every core-fix node (neither taxonomy-extension nor permanent-limitation) carries a positive blast-radius estimate — how much complexity the fix would add to Ariadne:

ValueMeaning
1A single-file edit
3A new function or resolver path
5A new cross-folder resolver pass
0Sentinel on taxonomy-extension and permanent-limitation nodes (no core fix to size; rationale empty)

The estimate must be grounded in code — the strategist reads the owning fault_area folder (the folder_anchor) to judge what Ariadne already supports — and the grounding is recorded in a non-empty core_fix_effort_rationale. The strategist assigns no priority or status: the cost integer is weighed against each task's benefit rollups (observed_count, projects, source_runs) by the human when promoting work.

The other bucket extends the taxonomy

When the bucket's fault_area is other, the deterministic derivation could not classify these false-positives — the bucket's descriptions[] carries the free-text signal. This is how the taxonomy grows: the strategist MUST emit both a taxonomy-extension task (is_taxonomy_extension: true — add the missing folder-anchored area to the AriadneFaultArea union and map the signal in derive_fault_area; grounded in the descriptions, so it may carry empty evidence_indices) and an underlying core-fix task grounded in evidence. The validator rejects an other plan missing either, and rejects is_taxonomy_extension on any non-other bucket.

Self-validate → iterate

validate_plan.ts is pure, structural, and deterministic: it takes the parsed plan plus the bucket context (bucket_fault_area, evidence_count, sweep_id) and returns { ok, issues[] }. The strategist loops write → validate → fix until ok === true; Pass C re-runs the same validator before reconciling, so a malformed plan is rejected at both ends. The rules it enforces:

Rule familyWhat is enforced
Envelopeschema_version === 1; fault_area in the taxonomy and equal to the dispatched bucket's; sweep_id echoes the dispatching sweep (guards against a stale plan from a prior sweep); non-empty roots
Tree structureA child's tier is strictly deeper than its parent's; every node's fault_area equals the bucket's; non-empty title/body
Evidence groundingevidence_indices in range and unique per node; a non-taxonomy localized leaf grounds at least one row
MembershipTotal (every index has exactly one verdict); a belongs: false verdict carries a non-empty reason; a suggested_area must be a real area and must not be the bucket's own (re-routing a member back into the bucket that excluded it never converges); no node grounds an excluded index
Cost axisA core-fix node carries a positive core_fix_effort + non-empty rationale; a taxonomy-extension or permanent-limitation node carries exactly 0
other bucketBoth a taxonomy-extension task and an evidence-grounded core-fix task exist; is_taxonomy_extension only on an other bucket

Pass C — Reconcile: commit the trees into the task-DB

reconcile_plan.ts loads each staged (bucket, plan) pair, re-validates the plan, flattens it into PlanTask candidates, and reconciles them against the live task-DB via JsonPlanTaskRepository — appending one PlanSweepEvent per decision to sweeps/<sweep_id>.jsonl.

Flatten: minting deterministic candidates

build_plan_tasks is pure and deterministic — the same plan + bucket yields byte-identical tasks. Per node:

  • Evidence aggregates up the tree: a parent's evidence is the union of its own evidence_indices and every descendant's (unioned by file:line identity), so a fault_area or architectural node's key is stable across sweeps of the same runs.
  • dedup_key is content-addressed: a hash of fault_area + the sorted evidence file:line set — nothing else. It is the immutable identity the whole loop dedups on, including the backlog's plan_dedup_key frontmatter.
  • Ids are minted from dedup_key + tier + pre-order ordinal (pt-<16-hex>), so two nodes legitimately sharing a key (a degenerate single-leaf subtree) still land in distinct files, while an identical re-sweep mints identical ids.
  • Every candidate starts status: "proposed" with wired parent_id/child_ids, rollups (observed_count, projects, source_runs), the strategist identity, and the node's core_fix_effort + rationale.

Reconcile: three decisions, in order

StepDecisionEvents
1. Create / augment A candidate whose dedup_key + tier names a live task (proposed) augments it: evidence merged by location, rollups recomputed, the current sweep's structural pointers adopted (remapped parent_id; child_ids unioned in), and the cost estimate refreshed from the candidate (the owning folder's capability evolves, so core_fix_effort is re-judged each sweep). Everything else is created fresh. Matching is 1:1 — exact id first (identical re-sweep), then a (dedup_key, tier) fallback for a moved-but-unchanged node; each existing task is claimed by at most one candidate. create · augment
2. Retire orphans A live task no candidate claimed is stale only when BOTH hold: (a) its grounding projects were all scanned this sweep (projects ⊆ the manifest's projects — a partial sweep never falsely resolves a task it didn't cover), and (b) its fault area is not in blocked_fault_areas (areas with a bucket this sweep but a rejected or missing plan — a plan failure must not read as "FPs stopped recurring"; an area with no bucket at all is unblocked). An eligible orphan sharing a file:line with a fresh create of the same (fault_area, tier) is superseded into it (one orphan) or combined (several → one), assigned by maximum location overlap; with no overlap, its false-positives stopped recurring → resolved — the bug appears fixed. supersede · combine · resolve
3. Export overlay A live written task whose dedup_key a backlog task already carries (the plan_dedup_key frontmatter stamped by the export adapter, read read-only) moves to status: "exported" and is suppressed from re-proposal. Suppression matches on (dedup_key, tier) so a promoted parent never suppresses a same-key leaf; a suppressed candidate is remapped to the real exported task's id so a surviving child re-parents onto a persisted node. The event fires exactly once, on the proposed→exported transition. export

Recording membership exclusions

Each plan's belongs: false verdicts are recorded three ways, turning one judgement into three durable signals:

  1. An exclude_member PlanSweepEvent — the audit trail.
  2. A record in the membership-override store, keyed on the flagged member's identity — drift-tolerant on (file_path, name, kind); start_line is a collision-breaker that can still shift, so a line-moved member re-enters the review. Pass A re-routes or suppresses it next sweep.
  3. When the verdict names a suggested_area, a derive_fault_area correction signal in the sweep summary (derive_fault_area_corrections[]) — the durable signal to fix the deterministic derivation itself, the same spirit as the other-bucket taxonomy extension.
The net guarantee: a re-sweep of the same runs augments rather than duplicates; an orphan whose false-positives vanished is resolved, not leaked; and work the human already promoted is suppressed, not re-proposed.

The planning-only write boundary

Plan proposes; it never actuates. Its entire write surface is its own task-DB under ~/.ariadne/plan/, and within the skill the reconcile pass is the sole writer of that surface — the strategist writes only its staged StrategistPlan.
