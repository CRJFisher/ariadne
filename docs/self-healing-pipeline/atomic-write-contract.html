Every shared surface in the pipeline has exactly one writer — and that ownership is enforced structurally, not by convention.

The Atomic-Write Contract and Write Boundaries

The classifier registry is a shared file that multiple processes could plausibly touch. Two mechanisms keep it safe and auditable: a locked read-mutate-write helper (atomic_update_registry) that makes concurrent mutation impossible to interleave, and an AST-level write-boundary test (registry_writers.test.ts) that fails the build if any code path bypasses the helper. Around them sits a write-boundary map giving every durable surface in the loop a single owner.

The locked read-mutate-write cycle

atomic_update_registry(registry_path, mutator) in packages/skill-fs/src/atomic_update_registry.ts is the only legal path to mutating a shared registry. It holds an exclusive lock over the entire read-mutate-write cycle, not just the final write:

The mutator returns a RegistryUpdate<R>, which lets read-only decisions skip the disk write entirely while still passing a result back to the caller:

type RegistryUpdate<R> =
  | { kind: "write"; next: string; result: R }   // commit `next` under the held lock
  | { kind: "noop";  result: R };                // release the lock without writing

Why bare atomic_write_file is not enough

atomic_write_file (temp file + POSIX rename) guarantees a reader never observes a torn, half-written file. It does not guarantee that two writers see each other. Two processes can each read the registry, compute independent mutations from the same snapshot, and rename their results in sequence — the second rename silently discards the first writer's mutation. That last-writer-wins data loss is exactly the race the .lock sidecar prevents: fs.open(path + ".lock", "wx") succeeds for at most one process at a time, serialising the full read-mutate-write cycles rather than just the final renames.

The lock is cooperative — only writers that go through atomic_update_registry honour it. A direct write bypasses it silently. That is why the contract needs a second, structural enforcement layer: the AST write-boundary test below.

Stale-lock recovery and the 5-second budget

Lock acquisition retries 100 times at 50 ms intervals (a ≈5 s budget), then throws could not acquire <path>.lock after 5000ms — stale lock?. Hitting the budget has two possible causes with two different cures:

CauseWhat happenedRecovery
Honest contention A slow mutator legitimately held the lock past the budget. A read-mutate-write pass over a registry of several hundred rules runs sub-second, so a real bump is evidence of a runaway loop. Increase the budget at the call site, or split the mutation into smaller transactions — after ruling out the runaway.
Crashed writer A previous writer was killed (SIGKILL, OOM, kernel panic, pkill -9) after acquiring the lock and before finally ran. The sidecar persists indefinitely. Verify no live writer holds the file (lsof <registry-path>.lock), then rm <registry-path>.lock.
Stale locks are never auto-broken based on mtime. The cure is worse than the disease: a false positive against a legitimately slow writer would interleave two mutators on the same registry — exactly the race the lock exists to prevent.

Structural enforcement: the AST write-boundary test

packages/skill-fs/src/registry_writers.test.ts turns the contract into a build gate. It walks every .ts file under .claude/skills/ and packages/ (excluding .test.ts, .d.ts, node_modules, dist), parses each with the TypeScript compiler, and flags two kinds of violation. Detection is purely syntactic and per-file — no cross-module data-flow analysis.

Violation 1: raw write against a registry-shaped path

Any call to one of the named write functions whose first argument resolves to a registry-shaped target:

write functions

atomic_write_file, writeFile, writeFileSync, appendFile, appendFileSync — matched by the rightmost identifier of the callee chain, so fs.promises.writeFile(…) is caught too.

registry-shaped first arg

A call to get_registry_file_path(…); an identifier or property access whose name carries registry (registry_path, opts.registry_path); or a string literal / template containing registry…json.

laundering defences

An identifier is chased to its same-file const x = … initializer, so splitting get_registry_file_path() into a local variable does not evade the check. A destructured alias of a registry-named key (const { registry_path: x } = opts) is treated as registry-shaped too.

Violation 2: any call to the registry serializer

Every call to serialize_known_issues_registry_json is flagged regardless of where its output goes. The function is narrow-purpose — it exists only to produce the registry's on-disk bytes — so calling it outside an atomic_update_registry mutator closure means somebody is computing those bytes and writing them without the lock, even when first-arg resolution would miss the writer (renamed binding, indirect helper, parameter passing).

The allowlists

AllowlistContentsWhy
ALLOWED_REGISTRY_WRITERS Exactly one file: packages/skill-fs/src/atomic_update_registry.ts Its body is the only legal direct write of the registry — it calls atomic_write_file while holding the lock. Every other site reaches the registry through it.
ALLOWED_SERIALIZER_CALLERS Empty Every legitimate write reaches the registry through an atomic_update_registry mutator, so no file may call the serializer at top level.

A violation fails the build with the offending file:line, the callee, and the first-argument text, plus the remediation: use atomic_update_registry(path, mutator) from @ariadnejs/skill-fs, or — if a new site is genuinely contractually permitted — add it to the allowlist and document the reason in .claude/rules/classifier-lifecycle.md.

The negative control

A scanner that silently stopped matching anything would still pass the main test, because the live workspace contains no real violations. A second test defends against that: it writes a synthetic known-bad file to a temp directory — one raw atomic_write_file("/tmp/registry.json", …) and one serialize_known_issues_registry_json call — runs scan_file on it, and asserts the scanner returns at least one hit of each violation kind. If a refactor breaks every branch of arg_targets_registry, this control fails instead of the boundary rotting silently.

The full write-boundary map

Single-writer ownership is one of the pipeline's three architectural invariants. Each durable surface that stitches the loop together has exactly one owner; everyone else is read-only. One writer per surface means every change has an unambiguous provenance — the loop stays auditable because "who wrote this row?" always has exactly one answer.

Two write disciplines, one rule. atomic_update_registry (lock + rename) is for the shared registry, where multiple potential writers must not interleave. Bare atomic_write_file (rename only) remains the contract for files with exactly one writer per path — per-entry verdict files, analysis-output JSON, the published results — where torn reads are the only hazard and a lock would buy nothing.
