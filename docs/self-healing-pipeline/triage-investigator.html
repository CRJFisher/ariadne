The Triage Investigator and the Verdict Union

A pool of Sonnet sub-agents, each handed one entry-point candidate, each emitting exactly one self-contained TriageVerdict file — pumped by a stateless picker that makes crash recovery automatic.

agent: .claude/agents/triage-investigator.md model: sonnet maxTurns: 50 one verdict per invocation

The worker-pool pump

The main triage agent runs a continuous worker pool over the residual entries — those neither auto-classified by a registry rule nor satisfied from the TP cache. It keeps the pool full by repeatedly calling get_next_triage_entry.ts, which does two things on every call:

  1. Merge — merge_results absorbs any completed verdict files from results/ into the triage state, flipping each matching entry's status from "pending" to "completed" (or "failed" when the verdict file does not parse). The verdict itself is not copied onto the entry — entry.result stays null. The verdict ledger lives on disk in results/; the state file is a pure control-plane log of routing and status.
  2. Pick — pick_next_entries returns up to --count entry indices that are status === "pending", not auto_classified, and not listed in --active. The picker never mutates a pending entry: there is no "claimed" or "in-flight" status on disk.

The --active double-dispatch guard

Because the picker never marks an entry as claimed, two consecutive pump calls would otherwise return the same pending index twice. The main agent prevents this in memory: it passes the comma-separated indices of currently in-flight investigators via --active, and the picker excludes them. In-flight tracking lives only in the live agent's context — never in the state file.

Crash recovery via pending re-dispense

That deliberate omission is the recovery mechanism. An investigator that dies mid-investigation leaves no verdict file, so its entry is still "pending" in state. When a run is resumed (or all of a prior run's investigators have died), the main agent simply calls the pump with --active omitted: every unfinished entry is re-dispensed as if never dispatched. No lease expiry, no janitor process, no claimed-but-orphaned status to repair.

Completion is double-gated. The pump flips state.phase to "complete" only when no investigatable entry is pending and --active is empty — so a run never finalizes while a worker is still in flight. Defence in depth: the picker also skips auto_classified entries even though build_triage_entries already marks them "completed", protecting against a regression that flips one back to pending.

Self-service context: get_entry_context.ts

Each investigator's prompt contains a project, a run_id, and an entry_index. Its first action is to fetch its own dispense payload:

node --import tsx .claude/skills/triage/scripts/get_entry_context.ts --project <project> --run-id <run_id> --entry <entry_index>

Entry indices are run-local, and the script derives the verdict output path from the run it resolves, so the orchestrator and its investigators pin the same run explicitly rather than each resolving the project's LATEST pointer.

The script loads the entry from triage state, loads the classifier registry, builds the payload via build_dispense_payload, and substitutes everything into a single prompt template. The investigator receives:

Payload sectionContents
entry_contextThe entry's name, file_path, kind, start_line, signature, export status, diagnosis, pre-gathered diagnostics (grep call sites and Ariadne call references with resolution_count, resolved_to, call_type, caller_function), and the exact output path for the verdict: results/<entry_index>.json.
Diagnosis hintsAn investigation guide keyed off the entry's diagnosis — callers-not-in-registry, callers-in-registry-unresolved, callers-in-registry-wrong-target — with a generic guide as the fallback.
Classifier hintsSub-threshold predicate matches: rules that matched this entry but fell below min_confidence for auto-classification, each with its group_id, confidence, and reasoning. A hint often names the exact detection gap.
relevant_registry_sliceThe wip + permanent classifier rules in scope for this entry (language or diagnosis_eq match, capped at 20, sorted by observed_count). This is the only registry material the investigator ever sees, and the citation universe for fp-classifier-regression.

From there the investigator gathers evidence with Read, Grep, Glob, and the mcp__ariadne__show_call_graph_neighborhood tool (to compare what the codebase contains against what Ariadne's call graph actually resolved), then writes raw JSON — no markdown fencing, no prose — to the supplied output path.

The TriageVerdict discriminated union

Defined in .claude/skills/triage/src/verdict/triage_verdict.ts: four kinds, each with its own required payload — no optional-everywhere shape. Every arm carries member_evidence ({ file, line, why }), so each verdict file is self-contained: downstream offline grouping in the plan engine needs no in-run consolidation.

KindMeaningPayload beyond member_evidencePublished at finalize as
tp Genuinely unreachable; the call graph is correct. — (the why records the search that ruled out callers) A confirmed_unreachable[] row with source: { kind: "llm-tp" }. Feeds the next run's TP cache at the same commit.
fp-novel A real caller exists and no in-scope rule should have caught it — a detection gap, i.e. an Ariadne defect. proposed_root_cause, evidence_excerpt One novel_issues[] row per verdict (no merging): id: "novel-<entry_index>", member_symbol, the investigator's evidence, plus deterministic core fault diagnostics (diagnosis, resolution_failure stage/reason, receiver_kind, disambiguator booleans) copied from the entry so the plan engine can re-derive the fault area from real values.
fp-classifier-regression A real caller exists and an in-scope rule's predicate intent covers it, but the predicate's current shape failed to match — the rule is too narrow. should_have_matched_rule_id, evidence_excerpt Rolled up per rule id by aggregate_classifier_regressions into classifier_regressions[] — the drift signal the human reads when authoring drift_evidence on a registry rule.
uncertain Cannot be reduced to a single verdict — compounding gaps, ambiguous evidence. reason (one sentence) An uncertain[] row, surfaced for human-tier review.

Why fp-classifier-regression must cite the slice

should_have_matched_rule_id must be a group_id from relevant_registry_slice. The regression verdict exists to power a cross-run drift signal on a specific rule the human owns: finalize aggregates flagged entries per rule id, and the human reads that slice when deciding whether a rule's predicate needs widening. A citation outside the in-scope slice is not actionable — there is no rule the human can inspect against the evidence — so the agent contract restricts citations to the rules the dispense payload actually delivered.

Strict parsing, no silent skipping

parse_triage_verdict is the single gate at both absorb time and finalize time (shared via the verdict ledger, so the two gates cannot diverge). It throws on any shape violation: unknown kind, missing fields, extra unknown fields, empty strings, or a non-positive-integer line. At absorb time a malformed file flips the entry to "failed" with the parse error recorded; at finalize, a completed llm-triage entry with no verdict file halts finalization with an instruction to re-dispense that entry. Verdicts are never partially accepted or quietly dropped.

The write boundary

The investigator never touches registry.json. Its only persistent output is the single verdict file at results/<entry_index>.json. It reads registry material only as the relevant_registry_slice embedded in its dispense payload. Every registry transition — including acting on the classifier_regressions[] its verdicts feed — is a human edit through atomic_update_registry. See Write Boundaries and Registry.

The boundary is enforced structurally, not just by instruction:

  • The agent's tool grant fences Write to ~/.ariadne/triage-entrypoints/** — the triage state tree where results/ lives. The repo-resident registry is outside the writable surface.
  • An AST-level write-boundary test (packages/skill-fs/src/registry_writers.test.ts) flags any code under .claude/skills/ that writes a registry-shaped path outside atomic_update_registry.
  • The state file itself stays a control-plane log: merge_results records only status transitions, leaving entry.result as null, so the verdict ledger on disk remains the single source of truth that finalize re-reads.
