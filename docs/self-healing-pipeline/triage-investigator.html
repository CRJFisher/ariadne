The Triage Investigator and the Verdict Union

One deterministic script investigates every residual entry-point candidate, each as a lean Agent SDK call that submits exactly one self-contained TriageVerdict — in a continuous pool that warms the prompt cache once and makes crash recovery automatic.

script: scripts/investigate_and_finalize.ts model: claude-haiku-5-5 · effort medium maxTurns: 20 one verdict per entry

The investigation loop

After Phase 2 prepares a run, the skill runs one command for Phases 3–4. No agent dispatches or coordinates investigations. Each call of investigate_and_finalize.ts:

  1. Claims — absorb_and_pick merges any verdict files already in results/ into the triage state (flipping each entry to "completed", or "failed" when a file does not parse) and picks every entry still to investigate: "pending", or "failed" with retry budget left. The verdict itself is not copied onto the entry; the state file is a control-plane log of routing and status.
  2. Investigates — a continuous pool of N concurrent investigations (default 8) with no batch barrier. The pool starts one lead and releases the other slots when the lead's first response arrives, so the shared prompt prefix is written to cache once and read by every later investigation.
  3. Writes — each accepted verdict to results/<entry_index>.json, and each investigation's usage (USD, turns, tokens, first-turn cache split) to investigations.json. An investigation that ends without a verdict is retried once; an entry whose second attempt also ends without one is recorded "failed".
  4. Finalizes — once nothing is left to investigate, finalize_run publishes the v5 results in the same call.

Stopping and resuming

A call stops starting investigations at the first of: the queue emptying, the --max-usd cap, an account error (spend limit, rate limit, auth), or its time budget (default 420 s, with investigations still running two minutes later aborted), so one call fits inside a 10-minute shell timeout. It prints a summary whose status is finalized, continue (run the same command again) or stopped. An entry whose investigation was cut short has no verdict file and stays "pending", so the next call simply re-investigates it: no lease, no claimed status on disk, no janitor. One call runs per run at a time, because a call claims every pending entry up front.

The cache is checked, not assumed. Every investigation records its first request's cache_read_input_tokens and cache_creation_input_tokens. The summary counts a prefix_miss for each investigation that started into a warm cache yet read under 90% of the shared prefix, so anything that makes the system prompt or tool definitions vary per investigation shows up in the run summary instead of silently raising its cost.

The investigation's prompt and tools

Each investigation is an Agent SDK query() that loads no Claude Code preset, settings, CLAUDE.md, hooks or other MCP servers. It writes 5-minute cache entries and sets a fixed session title, so it makes no extra title call. Its prompt has two parts:

PartContents
System prompt (constant)The verdict definitions and their pitfalls, what each evidence list means, the tool rules, the output contract, and the investigation guide for every diagnosis route (callers-not-in-registry, callers-in-registry-unresolved, callers-in-registry-wrong-target, callers-outside-indexed-corpus, references-without-call-syntax, and the generic no-textual-callers guide). It names no entry, so every investigation of every run shares it from the prompt cache.
First user message (per entry)The entry's name, kind, export status, definition file:line, signature and diagnosis; its grep call sites (each tagged with the call references captured at that line), Ariadne's call references (caller, receiver form, resolution targets, and an unresolved call's failing stage and reason, with its syntactic flags), out-of-index call sites and non-call reference sites; its sub-threshold classifier hints; and the in-scope classifier rules one line each (group_id: title — description, language match, capped at 20 by observed_count). Each evidence list shows at most 40 rows and names how many it left out, with a grep pattern that lists them. Paths are relative to the project root. get_entry_context.ts prints the same text.

Its three tools are served in-process: read (a numbered window of at most 200 lines), grep (a Perl-compatible search returning at most 100 matches) and submit_verdict. Both read and grep resolve every path inside the project root and refuse anything outside it. submit_verdict accepts a verdict only when it parses as a strict TriageVerdict, its member_evidence names a real line of the repository, and a regression cites an in-scope rule; otherwise it returns the reason and the investigation corrects it. The turn cap is 20.

The TriageVerdict discriminated union

Defined in .claude/skills/triage/src/verdict/triage_verdict.ts: four kinds, each with its own required payload — no optional-everywhere shape. Every arm carries member_evidence ({ file, line, why }), so each verdict file is self-contained: downstream offline grouping in the plan engine needs no in-run consolidation.

KindMeaningPayload beyond member_evidencePublished at finalize as
tp Genuinely unreachable; the call graph is correct. — (the why records the search that ruled out callers) A confirmed_unreachable[] row with source: { kind: "llm-tp" }. Feeds the next run's TP cache at the same commit.
fp-novel A real caller exists and no in-scope rule should have caught it — a detection gap, i.e. an Ariadne defect. proposed_root_cause, evidence_excerpt One novel_issues[] row per verdict (no merging): id: "novel-<entry_index>", member_symbol, the investigator's evidence, plus deterministic core fault diagnostics (diagnosis, resolution_failure stage/reason, receiver_kind, disambiguator booleans) copied from the entry so the plan engine can re-derive the fault area from real values.
fp-classifier-regression A real caller exists and an in-scope rule's predicate intent covers it, but the predicate's current shape failed to match — the rule is too narrow. should_have_matched_rule_id, evidence_excerpt Rolled up per rule id by aggregate_classifier_regressions into classifier_regressions[] — the drift signal the human reads when authoring drift_evidence on a registry rule.
uncertain Cannot be reduced to a single verdict — compounding gaps, ambiguous evidence. reason (one sentence) An uncertain[] row, surfaced for human-tier review.

Why fp-classifier-regression must cite the slice

should_have_matched_rule_id must be a group_id from relevant_registry_slice. The regression verdict exists to power a cross-run drift signal on a specific rule the human owns: finalize aggregates flagged entries per rule id, and the human reads that slice when deciding whether a rule's predicate needs widening. A citation outside the in-scope slice is not actionable — there is no rule the human can inspect against the evidence — so submit_verdict rejects a citation outside the rules the entry's context actually delivered.

Strict parsing, no silent skipping

parse_triage_verdict is the single gate at both absorb time and finalize time (shared via the verdict ledger, so the two gates cannot diverge). It throws on any shape violation: unknown kind, missing fields, extra unknown fields, empty strings, or a non-positive-integer line. At absorb time a malformed file flips the entry to "failed" with the parse error recorded; at finalize, a completed llm-triage entry with no verdict file halts finalization with an instruction to re-run the investigation loop. submit_verdict applies the same parser before a verdict is ever written. Verdicts are never partially accepted or quietly dropped.

The write boundary

An investigation never touches registry.json. It writes nothing at all: its verdict goes back through submit_verdict to the loop, which writes the single verdict file at results/<entry_index>.json. It reads registry material only as the in-scope rules in its first message. Every registry transition — including acting on the classifier_regressions[] its verdicts feed — is a human edit through atomic_update_registry. See Write Boundaries and Registry.

The boundary is enforced structurally, not just by instruction:

  • The investigation has no write tool: read and grep are read-only and confined to the target repository, and submit_verdict only hands the verdict back to the loop.
  • An AST-level write-boundary test (packages/skill-fs/src/registry_writers.test.ts) flags any code under .claude/skills/ that writes a registry-shaped path outside atomic_update_registry.
  • The state file itself stays a control-plane log: merge_results records only status transitions, leaving entry.result as null, so the verdict ledger on disk remains the single source of truth that finalize re-reads.
