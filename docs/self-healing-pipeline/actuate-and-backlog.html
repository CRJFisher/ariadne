Actuate: Prioritize, Export, and Closing the Loop

The autonomous sweep proposes; only a human promotes. This page covers the deliberate prioritize → export → commit flow that graduates planned work into the backlog, and the commit-scope convention that ties a landed fix back to the row it closes.

Human as sole actuator

Triage senses and plan classifies, but neither acts. Every state change that commits the project to work — writing a backlog task, authoring a classifier rule, flipping a registry row — is a human decision, executed through a write-fenced surface with exactly one writer:

SurfaceSole writerHuman's role
backlog/tasks/*.mdexport_to_backlog.ts (human-invoked)Selects which PlanTask rows graduate; the adapter is never run on the autonomous sweep.
.claude/skills/triage/known_issues/registry.jsonHuman via reconcile-registry → reconcile_registry.ts, always via atomic_update_registryAuthors wip rules, flips wip → permanent and wip → fixed.
packages/core/ (the actual fix)Human engineering workLands the fix with a task-scoped Conventional-Commits message.
Why a human fence? Each promoted task and each registry transition commits engineering effort or changes what triage suppresses on every future run. Keeping a single, deliberate writer per surface makes the loop auditable: every backlog task traces to a PlanTask via frontmatter, every registry flip traces to a human edit, and every landed fix traces to a commit scope.

The adapter pipeline: select → mint → render → write → flip

What each step does

  1. select — select_exportable_tasks (pure, in src/export/select_exportable_tasks.ts) picks the rows. Two modes: explicit (--id names exact rows; unknown ids surface as missing_ids, and the filter flags are ignored) or filtered (match on status, default proposed, plus optional fault_area and priority — the latter mapping to is_classifier_work). Selected rows are sorted by id for deterministic backlog-id assignment.
  2. mint id — next_backlog_task_id recursively scans the whole backlog tree (tasks/, archive/, completed/, drafts/) for the max task-<N> and returns N+1, so a minted id never collides with one retired into the archive.
  3. render — render_backlog_task reuses the PlanTask's already-rendered title/body (it never re-renders from a strategist plan), splits the body into Description and Acceptance Criteria regions, derives priority (high for core fixes, medium for interim classifier work), and stamps two link fields into frontmatter: plan_dedup_key (the verbatim PlanTask.dedup_key — the idempotency link) and plan_source_task (the source row id, for traceability). The fault area lands as a label alongside plan-export.
  4. write — atomic_write_file writes backlog/tasks/task-<N> - <slug>.md. This is the only place in the pipeline a write primitive appears against backlog/.
  5. flip state — the DB row moves to status: "exported" with exported_backlog_task: "TASK-<N>", and one export PlanSweepEvent is logged.

Idempotency: the plan_dedup_key guard lives in selection

Re-running the adapter with identical arguments is a no-op. The guarantee is enforced in selection, not at the write, by three guards applied to every candidate in order:

GuardDrops a candidate when…Reported as
DB statusthe row is already exported (with its exported_backlog_task)skipped_already_exported
Live-work fenceits status is terminal (superseded, resolved) — retired work named by a filter typo or an explicit --id; only proposed/accepted are exportableskipped_non_exportable
plan_dedup_keya backlog task already carries the row's dedup_key in frontmatter (read via read_exported_backlog_keys)skipped_already_exported
Crash safety: the third guard is what makes a re-run safe even if a prior run crashed after writing the backlog file but before flipping the DB row. The dedup_key, not the DB status alone, is the dedup authority. And because two live tasks never share a dedup_key (the plan engine's reconciler augments rather than duplicates), excluding terminal rows means no two selected rows can collide on a key — the duplicate-write path is structurally closed.

The stamped key becomes plan's read-only dedup signal

The same plan_dedup_key frontmatter field the adapter stamps is read back — strictly read-only — by src/store/backlog_dedup.ts during the plan engine's reconcile pass. read_exported_backlog_keys maps every promoted backlog task's plan_dedup_key → id from *.md frontmatter (a file counts only when it carries both id and plan_dedup_key; missing directories, non-markdown entries, and frontmatter-less files are skipped, never thrown — a sparse backlog is the normal early state).

The match is a structured frontmatter link, not a fuzzy text scan: when reconcile sees a re-derived task whose dedup_key a backlog task already carries, it recognizes work the human has already promoted and stops re-proposing it (the DB row moves to exported). Hand-authored backlog tasks carry no plan_dedup_key and are simply invisible to the engine — it has no DB lineage for them. The module uses readdir + readFile only: no write primitive, no backlog tool.

Commit scope: fix(<task_id>) ties the fix back

Once the human lands the actual core fix, the commit message is the audit trail. Commits use Conventional Commits with one extension: a commit that advances or resolves a backlog task uses the task id alone as its scope (no TASK- prefix):

fix(343): handle null receiver
feat(190.16.42): implement signal X
feat(190.17.12-14): batched retarget   # range; expands to .12, .13, .14

Multiple unrelated tasks in one commit (rare) use body trailers — Fixes:, Implements, Closes: — each naming a task that must exist in backlog/tasks/. A commit-msg hook validates task-shaped scopes (matching ^\d+(?:\.\d+)*(?:-\d+)?$) against backlog/tasks/; named-subsystem and unscoped commits pass through unvalidated, and CI re-validates the latest commit on every PR.

This parseable scope is what makes loop closure mechanical to verify while remaining human to perform: a classifier registry rule carries a backlog_task link, and when git log in the target repo shows a task-scoped commit matching that link, the human flips the rule's status to fixed. The KnownIssue schema stores no commit hash — the backlog_task link plus the git log are the entire audit trail. A fixed rule whose symbol resurfaces in a later run is surfaced for human review; there is no automatic re-flip back to wip.

The full cross-run cycle

Traced step by step

  1. Run N, triage: an investigator confirms a false positive (fp-novel); finalize publishes it in triage_results/<run-id>.json as a novel_issues[] row.
  2. Run N, plan: the sweep groups the issue into its AriadneFaultArea bucket, the strategist proposes a fix, and reconcile mints (or augments) a PlanTask keyed by its content-addressed dedup_key in ~/.ariadne/plan/tasks/.
  3. Human, prioritize: a --dry-run previews the proposed rows; the human weighs fault_area and core_fix_effort, narrows the selection, and drops --dry-run.
  4. Human, export: the adapter mints TASK-<N>, writes backlog/tasks/task-<N> - <slug>.md with plan_dedup_key stamped, and flips the DB row to exported.
  5. Human, fix: the engineering work lands in core with a fix(<N>): commit scope. Any interim classifier rule authored for this class sits in the registry as wip with backlog_task: TASK-<N>.
  6. Human, flip: seeing the task-scoped commit in git log match the rule's backlog_task, the human flips the registry row wip → fixed using reconcile-registry (via atomic_update_registry).
  7. Run N+1: triage's filter reflects the registry's current state; plan's reconcile reads the backlog's plan_dedup_key map and recognizes the work as already promoted, so it is not re-proposed. The defect class is healed end to end — and if a fixed rule's symbol ever resurfaces, it is flagged for human review rather than silently re-opened.
