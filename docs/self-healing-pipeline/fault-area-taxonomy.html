The AriadneFaultArea Taxonomy and dedup_key

AriadneFaultArea answers "which part of Ariadne's core is at fault" for each triage false positive — a folder-anchored taxonomy that is derived on every read, never stored — and two deliberately different content-addressed keys carry that grouping across sweeps.

Folder-anchored taxonomy

Every fault area except other is anchored 1:1 to the core module that owns the fix, via ARIADNE_FAULT_AREA_FOLDER. The plan engine routes each bucket's proposed work to that module. The map is a Record<AriadneFaultArea, string>, so adding an area to the union without naming its folder is a compile error.

A derived view: recompute-on-read, never persisted

The area is computed by derive_fault_area from the deterministic fault signal core already emits. Evidence on disk stores only the raw signal, never the derived area:

Persisted (raw signal)

  • diagnosis — plain string
  • resolution_failure — { stage, reason } as plain strings, or null
  • has_uncaptured_indexed_grep_hit — boolean
  • callers_only_in_unindexed_tests — boolean

Derived (computed on read)

  • area — the fault area
  • resolution_stage / resolution_reason — echoed when known enum members
  • needs_judgement — strategist must adjudicate
  • description — present iff area === "other"
Why recompute-on-read. A stored area would be a snapshot of the taxonomy as it stood at write time — a type lie the moment the taxonomy moves. Because only the raw signal persists, a core IA refactor edits exactly one thing (ARIADNE_FAULT_AREA_FOLDER) and every past evidence row immediately re-derives against the current taxonomy.

Raw strings, not enums — by design

DeriveFaultAreaInput types stage, reason, and diagnosis as plain strings even though core emits typed unions (ResolutionFailureStage, ResolutionFailureReason, EntryPointDiagnosis). The asymmetry is deliberate, and it cuts both ways:

  • At the read boundary: a forward-incompatible value — one a newer core emits but this package does not yet know — routes to the other escape hatch at runtime instead of being a type error or a misparse.
  • Inside the derivation: the internal tables (REASON_TO_AREA, the stage and diagnosis sets) are Records over the typed unions, so a new enum member added in code is a missing-key compile error until it is mapped.

An other result carries a free-text description naming the unrecognized value; the plan engine reads that description both to extend the taxonomy and to plan the underlying fix.

derive_fault_area precedence

derive_fault_area is a pure, total function. The per-call ResolutionFailure is the most specific signal and is consulted first; the summary diagnosis is the fallback when no failure was emitted. Within the fallback, the coverage-gap boolean wins over the diagnosis itself.

Precedence rules in detail

  1. Per-call resolution_failure. When present, REASON_TO_AREA maps the reason to its area. method_not_on_type is the sole stage-ambiguous reason: stage method_lookup → method_lookup; any other known stage → receiver_type_inference; an unrecognized stage cannot break the tie and routes to other. An unrecognized reason routes to other immediately.
  2. Coverage gap before diagnosis. When every caller lives in a directory excluded from indexing, the indexed grep finds nothing and the diagnosis reads no-textual-callers even though real callers exist. Routing on the diagnosis alone would misread this as a genuine entry point, so callers_only_in_unindexed_tests is consulted first and wins → coverage_config.
  3. Diagnosis switch. no-textual-callers → entry_point_classification; callers-in-registry-wrong-target → entry_point_classification; callers-in-registry-unresolved (with no failure emitted) → other; callers-not-in-registry → syntactic_extraction, deterministic when has_uncaptured_indexed_grep_hit is true.

When the deterministic routing does mis-bucket a member, the strategist excludes it from its plan and the reconcile pass records the exclusion in the membership-override store, keyed on member_identity_token — so the next sweep's deterministic re-derivation re-routes (or suppresses) it instead of re-adjudicating forever.

Two content-addressed keys, deliberately different

Two key primitives carry fault-area work across sweeps. They answer different questions, so they are built from different inputs and are never interchanged.

dedup_key — the reconciliation primitive

location_token is the load-bearing piece: the "<file>:<line>" identity of one evidence row's call site. compute_dedup_key hashes the sorted set of those tokens, union_evidence deduplicates on them, and the reconciler overlap-scores orphans against fresh creates on them — so the recipe lives in one place and must agree byte-for-byte across all three sites.

location_token(evidence)  =  `${member_evidence.file}:${member_evidence.line}`

dedup_key  =  sha256( [fault_area, ...sorted(unique(location_tokens))].join("\n") )
  • Inputs are fault_area + the location set only — never title, body, tier, status, the rollups, or provenance. A re-sweep of the same proposal hashes identically regardless of wording.
  • Pure and order-insensitive: same area + same location set, in any order, with any duplicates ⇒ same digest.
  • Newline-joined payload so a : inside a file:line token can never collide with the delimiter.

member_identity_token — the override-store key

member_identity_token(member)  =  [file_path, name, kind, String(start_line)].join("\n")

override_key  =  `${fault_area}\n${member_identity_token(member)}`
  • Keyed on the flagged member, not its callers' call sites. (file_path, name, kind) is the drift-tolerant core; start_line is the same-name/overload collision-breaker.
  • Line shifts invalidate deliberately: start_line moves when surrounding lines shift, so the token matches only while the member's start line is unchanged — a line-shifted member re-enters strategist review rather than inheriting a stale exclusion.
  • Scoped per area: the override key prefixes the area, because the same member may be a member of — and correctly excluded from — more than one area's bucket over time.
Why two primitives. dedup_key reconciles a task by the exact set of call-site locations grounding it (exact-overlap equivalence); member_identity_token routes a single member across sweeps. A task gains or loses evidence rows without the member's identity changing, and a member shifts lines without its task's call sites changing. Different questions, different primitives — dedup_key is not re-keyed onto member identity.
