Every member carries the identity of the type it belongs to

The lexical scope tree is built by pure positional containment and records no type identity. One nullable field — enclosing_type_id on LexicalScope — stamped at the PASS 3 seam, makes every method and constructor scope name its owning class/struct, regardless of which physical body block declared it.

Resolve the scope→type edge once, from definitions that are already type-unified, and key it on a location-anchored SymbolId — never a name.

Collision safety — why a location-anchored SymbolId is correct

The key is ClassDefinition.symbol_id — a location-anchored SymbolId, not a name. Because the edge comes from each method's already-resolved definition at the PASS 3 seam, every collision case is already handled by the definition layer PASS 3 just ran.

Every file:line the plan cites was checked against the current source. The data-model claims hold exactly; three points warrant the implementer's attention.

Confirmed exact

All cited sites match: the 6-field LexicalScope with no enclosing_type_id (index_single_file.ts:29-47); construction literal scopes.ts:233-240; the block special-case :401-405 and reverse-scan :423-458 in receiver_resolution.ts; constructors landing only in by_symbol not flat_members (definition.ts:159-166); @scope.block / @scope.constructor captures.

Note 1 · two sites emit no_parent_class

no_parent_class is emitted at two sites sharing one reason-string: the Python-constructor positional walk in function_call.ts:82-91 (the case this work fixes) and the super-keyword no-parent failure at receiver_resolution.ts:201 (unaffected). The "stops being emitted" claim applies to the constructor site only.

Note 2 · enums are NOT in member_index today (open question #3 confirmed)

definition.ts has no enum branch — member_index keys only class/interface (:134). A Rust enum-method lookup would stamp enclosing_type_id = id_Enum yet find no member_index entry under that key, so §3.2's widening must extend to enums. A real gap, not hypothetical.

Note 3 · extract_impl_boundaries is dead but the symbol_location differs

Confirmed dead at rust_scope_boundary_extractor.ts:142-162 (the impl body is @scope.block, so case "impl_item" never fires); the plan's deletion is sound. The realigned tests (§8.3) must assert the live block path, not the removed synthetic dispatch.
