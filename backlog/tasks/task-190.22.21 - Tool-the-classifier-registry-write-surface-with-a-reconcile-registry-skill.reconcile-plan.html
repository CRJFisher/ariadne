Plan: reconcile-registry — Tooling the Registry Write Surface

The classifier registry is the one human-owned write surface in the pipeline with no tooling — every transition is a raw hand-edit of a 180-rule JSON file, and the reconciliation work simply isn't happening. reconcile-registry will be the registry's exact analogue of prioritize: a thin, human-invoked decision skill over a single fenced writer that detects work already done and proposes the mechanical flips.

The asymmetry: three surfaces, one untooled

The pipeline has three human-owned write surfaces. The backlog has a decision skill plus a fenced writer; core fixes are human engineering by design. The registry — the middle row — has nothing. This plan fills exactly that cell, fulfilling what the actuate doc already promises: "Human (hand edit or human-invoked script, always via atomic_update_registry)". The script was never built.

Scope: three mechanical writes, nothing more

The skill never authors rule prose and never makes the permanent judgment — those stay human creative work. It detects three high-confidence signals, proposes the corresponding writes, shows the diff, and on confirmation writes through the one fenced writer:

#Signal (mechanically detected)Proposed registry write
1git log scope matches a wip rule's backlog_task (reusing the scope parser in scripts/check-commit-message.ts)wip → fixed
2published triage_results[].classifier_regressions[] names a rule_idset drift_detected: true; append new drift_evidence[] rows (append-only, deduped by entry_index — re-runs are idempotent)
3human elects to promote a rule to permanent (--id <group_id> --promote)flip the status and regenerate permanent_data.ts; the sync test guards it thereafter

Preview → narrow → apply

The workflow mirrors prioritize exactly: a --dry-run scans every signal and prints the proposed changeset writing nothing; selectors narrow the set; dropping --dry-run applies through atomic_update_registry — one lock-fenced read-mutate-write per invocation.

Selectors (mirroring prioritize)

FlagEffect
--dry-runScan every signal and print the proposed changeset, grouped by transition; writes nothing. Always the first run.
--fixedRestrict to wip → fixed proposals (git-log scope matches).

Same shape as prioritize, deliberately. The skill owns no logic of its own, drives a single script, and is disable-model-invocation: true — only a human can trigger it; the model never self-invokes. The scripts live under .claude/skills/triage/scripts/ because that is where the registry and its loaders already live, exactly as prioritize points at a script under plan/scripts/.

Which lifecycle arrows this mechanises

The lifecycle diagram shows every transition as a human edit. That stays true — the human remains the decider on every arrow. What changes is that two arrows gain a detector (the signal is found mechanically and proposed) and one gains a mechanical apply-step (the regeneration the lifecycle doc already describes but nothing performs):

Enforcement: the surface stops relying on memory

Cheap writes alone don't guarantee the registry gets written. Two structural guards make the surface enforced, paralleling the existing AST write-boundary test:

permanent_data.sync.test.ts (new)

Asserts the committed permanent_data.ts byte-equals the slice freshly generated from the source registry. The bundled core slice can never silently drift from the registry: a hand-edit to either file fails CI. This gives the "AUTO-GENERATED" header teeth for the first time.

registry_writers.test.ts (existing)

The AST walk in packages/skill-fs/src/registry_writers.test.ts already flags any raw write primitive against a registry-shaped path. reconcile_registry.ts reaches the registry only via atomic_update_registry, so it is compliant by construction — and the existing test proves it, with no new allowlist entry.
