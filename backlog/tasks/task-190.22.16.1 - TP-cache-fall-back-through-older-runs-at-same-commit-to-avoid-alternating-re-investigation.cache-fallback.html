TP cache: fall back through older runs at the same commit

status To Do priority medium labels self-repair · bug parent TASK-190.22.16
The fix in one sentence

When the most recent run at the current commit has no reusable llm-tp verdicts — because that run was itself a cache-reuse run — keep walking back through older finalized runs at the same commit until one yields a non-null cache, instead of giving up and re-investigating everything with the LLM.

The alternating cadence

Each run derives its cache from prior published results at the same commit. build_cache only indexes rows with source.kind === "llm-tp" — a reuse run's output (all previously-confirmed-tp) yields nothing. Because derive_tp_cache consults only the single most recent run, every second run finds an empty source and pays the full LLM cost again.

Where it breaks

Two pieces interact. The eligibility filter (landed in TASK-190.22.16) is correct and stays: a cache hit is never itself reused, because the published row carries no origin chain. The defect is in run selection — a single lookup that trusts whatever the lex-max run happens to contain.

}

The fix: fall back through older runs

1

Add all_finalized_runs_at_commit(project, short_commit)

Returns every finalized run whose run-id starts with <short_commit>-, sorted lex-descending — the ISO-timestamp suffix makes lex order chronological, so index 0 is the newest run. Generalizes the directory scan that most_recent_finalized_triage_results already performs.

.claude/skills/triage/src/store/triage_results_store.ts (new export)
2

Iterate newest-first in derive_tp_cache

Replace the single lookup with a loop that returns the first non-null cache. A run whose rows are all previously-confirmed-tp (or all registry) is skipped; the loop lands on the run that holds direct LLM verdicts. The pinned-source path (--tp-source-run) is untouched.

Open question for the implementer

The spec's loop calls build_cache(run.run_id, run.output), which implies all_finalized_runs_at_commit eagerly reads and parses every run file at the commit before the loop starts. Returning run-ids only and reading lazily inside the loop (read_triage_results per iteration) preserves the early-exit read bound. Files are KB-scale either way, so eager is acceptable — but pick one shape deliberately and let the store tests assert it.

Why this terminates

Within one commit there is at most a handful of finalized runs, and the first run at any commit is always a full investigation (no prior runs to reuse from), so the loop always has an llm-tp floor to land on — unless every confirmed-unreachable verdict at that commit came from registry rules, in which case null is the correct answer: registry rows must stay live against rule deactivation and are never cached.
