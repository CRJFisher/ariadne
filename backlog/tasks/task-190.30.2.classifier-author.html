self-healing pipeline · classifier registry · authoring gap

When triage finds a permanent limitation, an agent drafts its classifier and the human inserts it under lock

After 190.30.1 the registry is a permanent-limitations catalog — 22 entries, all firing. But when triage surfaces a new permanent limitation, there is no tool to turn it into a classifier: the human hand-writes the predicate or builtin from scratch.

190.30.2 adds a classifier-author agent that drafts a validated KnownIssue into a staging directory, plus a reconcile_registry.ts --stage path that validates that draft and — with --apply — inserts it through the lock-fenced write contract. The agent never touches registry.json.

Every arrow that reaches registry.json is human-operated. The agent only ever produces a staged draft; the human runs --stage, which validates against the KnownIssue schema and writes through atomic_update_registry. This is why the AST-walk in registry_writers.test.ts still passes — no agent code path calls a raw write function against the registry.

02The agent's core decision: predicate first, builtin only when the DSL can't say it

The agent prefers predicate — a serialisable JSON tree over the 17 PredicateExpr operators in packages/types/src/known_issues.ts, evaluated with no TypeScript compile step. It falls back to builtin — a named check_*.ts function in packages/core/.../builtins/ — only when the pattern needs logic the closed DSL cannot express.

The 17 operators the agent composes into an expression tree — combinators all · any · not plus leaves like diagnosis_eq · decorator_matches · grep_line_regex · receiver_kind_eq · has_unindexed_test_caller. The live builtin check_string-keyed-dispatch (Angular ɵɵ-prefix + core file-path regex) is exactly the file-path-regex case that forces the fallback.

03The --stage insertion path: four gates before any write, dry-run by default

This is the concrete, testable half of the task — a new subcommand on reconcile_registry.ts. It reuses the existing validate_registry / evidence-gate machinery in known_issues_registry.ts. Each gate is a hard reject (fail-loud, no silent skip); only after all four pass does a dry-run print the entry — and only --apply writes, through atomic_update_registry.

deliberate safety inversion — call this out at review

--stage is dry-run by default and writes only with --apply. This inverts the rest of reconcile_registry.ts, where every other signal applies by default and previews with --dry-run. Insertion of a brand-new catalog entry is the higher-stakes operation, so its default is the safe one. Worth confirming this asymmetry is intended and documented.

Gate 3 rejects a builtin draft whose function_name is absent from BUILTIN_CHECKS, forcing the human to place the .ts and rebuild first. Gate 4 is 190.30.1's evidence gate on the authoring path — observed_count < 1 is a speculative, never-observed classifier, refused.

known_issues_registry.ts · validate_entry() — the evidence gate that gate 4 reusesverbatim
// Evidence gate: a wip entry that carries an authored classifier must have
// fired in a real triage run (observed_count >= 1).
const classifier = record["classifier"] as { kind?: unknown };
if (record["status"] === "wip" && classifier.kind !== "none") {
  const observed_count = record["observed_count"];
  if (typeof observed_count !== "number" || observed_count < 1) {
    throw new RegistryValidationError(
      `${at_id}.observed_count: a wip entry with an authored classifier ` +
      `must record observed_count >= 1`,
    );
  }
}
