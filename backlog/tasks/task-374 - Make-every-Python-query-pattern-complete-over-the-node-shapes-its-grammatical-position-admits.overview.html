Leverage beyond the counted rows
  • Erasure multiplies. One uncaptured class removes every method it owns; one duplicate-export throw blanks an entire file's resolution. The row counts are the visible floor, not the ceiling.
  • Whole shape families are restored, not single evidence rows — call-shaped decorators (@lru_cache(maxsize=1), @app.route(...)), every @classmethod, every qualified or generic base class, every this.-rooted read in every TS/JS project indexed.
  • Correctness beyond reachability. Inert predicates at python.scm:838-844 currently capture every Python identifier as @reference.this, three times over; deleting 7 duplicate patterns removes doubled references and doubled edges throughout.
  • An invariant lands with the fix — a definition-node coverage audit plus a duplicate-capture assertion over the fixture corpus, so this class of erasure cannot silently return.
Honest limits — the other ~18 rows do not close here
~10 accessor rows with a bare identifier receiver already mint their reference today; their residual failure is receiver typing and they re-triage after this lands. 2 typeorm tagged-template rows are a proven no-op — the grammar models a tagged template as a call_expression, so it is already captured. webpack unpack and lodash updateLogRow are receiver typing and anonymous-scope construction; boot.js obj[key] is runtime-computed dispatch and belongs to the permanent-limitation leaf. The verification also falsified the original framing ("add a reference kind per invocation form"): plain calls, tagged templates and accessor resolution all already work — only the capture never fires.

Risks to price in
  • Index volume (the real cost). Widening the member read multiplies property_access references on TS/JS-heavy repos, and each one runs the full method-call machinery. Measure index size and wall-clock on angular and prisma before/after; fallback is to exclude reads in a call's function position.
  • Over-capture, not collision. No new key is minted; over-capture is filtered by machinery that already exists (getter-only filter, setter shadowing guard). Getter over-approximation widens with the receiver set — watch polymorphic_dispatch rows.
  • Snapshots move deliberately. JSON index snapshots change; regenerate and review the diff for fabricated edges. The capture/receiver-consistency Stop hook must pass — every deleted pattern's handler is checked for orphanhood.
  • One external dependency. The dotted-extends parent link lives in registries/type.ts:245 and is name_resolution work; the 2 sqlalchemy super() rows close only after it.

Fund this when you want breadth per unit of design risk. The mechanism is subtractive — delete shape-specific patterns and let builders that already handle every shape do the discriminating — so most of the diff removes code rather than adding it, and the only genuinely new construct (the callable-value reference) is isolated in step 7. The counter-argument is that step 5 alone can grow the index on large TS/JS repos, and that ~18 rows in the bucket are receiver-typing or scope-construction problems this cluster will not touch. Steps 1-4 carry most of the yield at almost none of that cost and can be funded on their own.
