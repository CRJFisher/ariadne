TASK-349 · resolve_references / receiver_type_inference · refactor

Carry receiver types into receiver_resolution

A receiver's type is knowable at a declaration or assignment site, but the fact never reaches a form the call resolver can consult — so this.field.method() / self.df.method() fail and the callee surfaces as a false entry point. One shared structural feeder fixes all three core leaves.

34 observed members 8 projects 4 sub-tasks 3 core leaves · 1 classifier consult-side edits: 0 verdict: sound-with-corrections

One structural cause, three languages

Each leaf is the same failure at a different capture site: a known type fact never lands as a resolvable carrier on the definition, so the single consult site reads null.

Unifying insight

All three core leaves are the SAME failure — a receiver type is known at a declaration/assignment site but never reaches a consultable form — so the refactor builds one shared typed-binding feeder and each leaf becomes a thin language adapter, not a bolt-on patch.

The single consult site is walk_property_chain (receiver_resolution.ts:301-370). It reads get_symbol_type(member) first, then a def.type fallback; when neither yields a type it emits method_not_on_type / member_type_unknown. The resolver is starved of type carriers, not broken — the fix is almost entirely capture-time, and the consult side needs zero edits.

The shared producer contract

Every typed definition slot (param / local / property) carries up to two optional, unresolved carriers: type?: SymbolName (a bare name) and the new type_namespace_chain?: readonly SymbolName[] (a dotted chain like ['pd','DataFrame']). Language-specific capture adapters fill them; downstream resolution is byte-identical for all three leaves.

The type-propagation path — current vs planned

A type fact must travel from a declaration site to symbol_types, OR resolve directly through the consult-side fallback. Today the carrier is fed inconsistently (rust edges break); the refactor normalizes the carrier at capture time so every path reaches a resolvable name.

Path B — def.type fallback (consult-side) Path A — symbol_types funnel (STEP 1b) broken edge today added / normalized

Two independent consult paths — the load-bearing subtlety

The verifier flagged this: walk_property_chain can be satisfied two ways, and each leaf relies on exactly one. Treating the funnel as the only convergence point is wrong — the def.type fallback is load-bearing.

Why this matters for scope (YAGNI)

For 349.1.1 and 349.1.2 the cheaper Path B is enough — the bindings/symbol_types additions are not required. The funnel additions are required only for 349.1.3. Each leaf declares which path it relies on, backed by a test that proves it: success with symbol_types empty (Path B) vs requiring it populated (Path A).

Risks & open questions — honestly

The plan was rated sound-with-corrections. The highest-risk assumption is whether the construction classes are even in the indexed corpus; below it, the corrections the verifier folded in.

highest risk — hard precondition gate

Is pandas even in the indexed corpus?

If pd.DataFrame/Series/HDFStore classes are external (not indexed), resolve_namespace_export (type.ts:242) returns nothing and no in-repo fix resolves 349.1.3. STEP 1b also needs import_kind==='namespace' and a resolvable source file — preconditions beyond mere in-corpus presence.

mitigation — validate each of the 9 pandas members against the actual fixture corpus at step 0; route external ones to 349.1.4. This is why the classifier lands first.

verify empirically — open question 2

Is a property's location in get_symbol_at_location?

STEP 1 keys on get_symbol_at_location(loc_key) (type.ts:204) and skips when no symbol is registered there. If a property's location is not registered, Path A cannot populate symbol_types for properties at all, and STEP 1b's namespace write silently no-ops — leaving Path B the only working property path.

mitigation — empirically verify before relying on the funnel for the Python leaf.

behavioral — competing properties

Dropping the __init__ filter

add_property_to_class keys by location, so the same self.X in two methods yields two distinct PropertyDefinitions; member_index is last-writer-wins by name.

mitigation — pick a deterministic canonical site (prefer __init__/first declaration); add a test asserting the canonical type wins.

test blast radius

Existing Python property-set tests break at step 4

Many tests assert a class's property set with toEqual against __init__-only attrs. Widening capture adds properties and breaks those assertions.

mitigation — update the affected literals as part of step 4; the "tests stay green" guarantee holds only through step 3.

Corrections folded in from the adversarial review

REFUTED
"All three converge on populating symbol_types."

The consult-side def.type fallback (receiver_resolution.ts:332-356) is load-bearing and was ignored. For 349.1.1/349.1.2 the capture-time fix alone resolves via Path B with symbol_types never populated.

↳ folded in: each leaf now declares its path, with a test that distinguishes A from B.

REFUTED
"A namespace-chain carrier already exists for variables."

VariableDefinition has only type?: SymbolName; the variable namespace path derives from a constructor reference (extract_constructor_bindings), not a def field. type_namespace_chain on PropertyDefinition is a genuinely new kind of carrier.

↳ folded in: the producer-contract section reframes the precedent as reference-derived, and lists add_property_to_class as a required edit.

REFUTED
"Seed tests via set_test_resolutions."

No such helper exists; symbol_types is private. The named helper is fictional.

↳ folded in: tests use register_late_binding(symbol_id, type_id, file_path) (type.ts:421) or drive the full update_file path.

REFUTED
"349.1.1 is a one-line change covering its evidence."

A material fraction of the 14-member evidence (Rust operator-indexing, django module-qualified chain) is not touched by generic stripping, and optional/readonly fields already resolve at HEAD.

↳ folded in: explicit evidence triage routes the out-of-scope shapes to 349.1.4; regression guards lock the already-working shapes.
