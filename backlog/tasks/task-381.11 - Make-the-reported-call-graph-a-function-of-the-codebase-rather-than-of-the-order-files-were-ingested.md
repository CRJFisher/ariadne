## Description

<!-- SECTION:DESCRIPTION:BEGIN -->

The same file set in a different ingest order produced a different call graph, on the unpatched build as much as on everything this epic adds. The mechanism has now been found, and it is not where the earlier hypothesis put it. `fix_import_definition_locations` (`packages/core/src/project/fix_import_locations.ts:66`) rewrites every `ImportDefinition`'s `location` to the exact location of the definition it names in the other file, so that "go to definition" on an imported symbol jumps to the declaration. `DefinitionRegistry.update_file` then keyed `location_to_symbol` on `location_key(def.location)` for EVERY definition including imports (`registries/definition.ts:116-117`), so one symbol's declaration location was claimed by the declaration and by every file that imports it; the map holds one value, so the survivor was whichever file was written last. `remove_file` (`:355-356`) made it worse by deleting the declaration's key outright when an importer was evicted.

Nothing about that is order-dependent on the incremental `update_file` path, which is why it survived so long. It bites only on the BULK path: `resolve_corpus` (`project/project.ts:204-222`) runs Phase 2.5 for every file before `resolve_files` runs for any, so by the time Phase 4 asks `definitions.get_symbol_at_location` for a constructor binding (`registries/type.ts:155`) the key may answer with an importer's import symbol instead of the declaration. The type is then bound to the import symbol, `types.get_symbol_type(declaration)` is null forever, and every `x.method()` through that symbol fails at `receiver_type_unknown` (`call_resolution/receiver_resolution.ts:285`), making its methods look unreachable. The affected shape is vscode's exported-singleton idiom — `export const extUri = new ExtUri(...)`, `export const IME = new IMEImpl()`, `export const Registry: IRegistry = new RegistryImpl()` — imported and used from more than one file. A ten-line synthetic case pinned it before any product code was touched: same three files, two orders, `symbol_at_decl_location` the declaration in one and an importer's import symbol in the other, 0 versus 2 resolved edges.

A second, independent order-dependence was found only by adding a seventh number to the fingerprint. `IndirectReachability` is keyed by the reachable function, but many files can read that function as a value and only one read site is stored as the reported evidence; four writers each picked by walk order — three sites in `indirect_reachability.ts` (last-wins), `callable_value.ts:41` (first-wins), the `call_resolver.ts:143` merge (first-wins) and `resolution_state.ts:290` (last-wins). This never moved entry-point membership, which is exactly why the six-number fingerprint could not see it. The fix is a `def.kind !== "import"` gate on the location index in both `update_file` and `remove_file` — the same carve-out `by_scope` already makes two lines below, and all four readers of that index want a declaration — plus a single writer `record_indirect_reachability(into, fn_id, entry)` that keeps the read site earliest in the project by file path, then line, then column, with every competing writer routed through it.

The earlier diagnosis in this task is REFUTED and must not be planned against. `by_symbol` insertion order in `get_callable_definitions` (`call_resolver.ts:456`) is not part of the answer: four ingest orders necessarily produce four different insertion orders and, after the fix, one byte-identical fingerprint. The prototype that appeared to implicate it moved the graph because re-inserting only a file's imports changed which symbol won a shared `location_to_symbol` key. The phase-2 suspicion of state accumulated inside `resolve_type_metadata` or `extract_constructor_bindings` is also refuted: the sensitivity is created in Phase 2.5, before a single name is resolved, and resolution was faithfully reading a corrupted index.
