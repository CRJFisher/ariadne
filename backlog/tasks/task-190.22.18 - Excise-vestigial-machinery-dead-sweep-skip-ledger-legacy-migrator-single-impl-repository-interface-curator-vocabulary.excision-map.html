Item 3 — should plan_task* types leave the shared package?

Deleting the interface leaves PlanTaskQuery and PlanSweepEvent homeless. The deeper question: @ariadnejs/skill-protocol is the triage↔plan shared contract — but triage never imports plan_task* (grep-confirmed: zero hits under .claude/skills/triage/). So the plan-task types are not actually shared.

shared import plan-only — not shared proposed home
Decision A — recommended: move Keeping plan_task* in the shared package implies a seam that does not exist. Moving them into the plan skill makes skill-protocol hold only what triage and plan genuinely share, and gives the surviving PlanTaskQuery/PlanSweepEvent their home. The lighter alternative — leave them in skill-protocol, just delete the interface — is the smaller diff but leaves the "shared" lie in place.

The two genuinely open decisions

Everything above has a recommended path. These two need your call before the moves land.

Decision A

impact_report.ts — which home?

Imported only by scripts/generate_impact_report.ts (grep-confirmed). It is not pipeline-pass code — it is standalone registry tooling that happened to sit in propose/.

Own module — src/impact_report/lean

Honest, self-naming home matching its single concern; carries its __fixtures__/ with it.

Beside its script — scripts/

Co-locates with the only caller, but mixes library code into a scripts folder.

Decision B

render_unsupported_features.ts — stay or go?

Its only importer is its own .test.ts. But it is the generator-of-record for committed core docs (packages/core/…/queries/unsupported_features.{lang}.md, which exist on disk). No SKILL.md references it.

Keep — relocate to core toolinglean

It regenerates committed core artifacts, so it belongs near packages/core, not in the plan skill. Deleting it orphans the generator of files still in the tree.

Delete

Defensible only if the core docs are now hand-maintained — which makes the committed .md files the source of truth. Needs confirmation they are no longer regenerated.

Why these two are open Both are standalone tooling with exactly one caller — so the import graph alone does not dictate a home, and the right answer turns on intent (is the artifact still regenerated?) rather than on a dangling reference. The other five items are mechanical: grep proves the code is dead or the move is safe.
