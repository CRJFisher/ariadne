The crux: the export registry refuses to surface a definition that the importer explicitly names

The defining symbol already exists in the DefinitionRegistry keyed by (file, name). The chain breaks only because ExportRegistry.add_to_registry drops non-exported symbols, and Phase-1's import binding goes through that registry.

chain breaks at the gate symbol exists in DefinitionRegistry verified: capture_handlers.python.test.ts:1388–1406

The fix: widen the explicit-named-import lookup to a by-name DefinitionRegistry fallback

When the is_exported-gated export set has no entry for an explicit named import, fall back to the by-name DefinitionRegistry lookup in the source file. The caller at name_resolution.ts:166 picks this up automatically.

registries/export.ts — explicit-named-import fallback (the is_exported gate stays for everyone else)
// CURRENT — add_to_registry drops every non-exported symbol (export.ts:89):

// CHANGE B — explicit-named-import resolution falls back to the definition
// registry when the gated export set has no entry:
if (import_kind === "named" && !gated_export_hit) {
  resolved = definitions.get_by_name(source_file, import_name);  // (file, name) key

riskiest part — keep the gate for everything that is NOT an explicit named import (AC #4)

is_exported=false correctly models "not part of the public surface." The fallback must fire only for an explicit named import. Wildcard (from .x import *), namespace, and re-export paths must keep gating on is_exported — widening them would surface private names into public re-export chains, which is wrong.
