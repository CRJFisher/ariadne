The path-prefix is type-last — the final segment is the type

Unlike a function call (where the terminal is dropped from the prefix), a constructor's path_prefix keeps the full type path: leading segments are the module path, the final segment is the type that owns new.

The walk reuses the module/type path resolver introduced for function calls in 349.1: resolve the leading segment to a mod/use module or type, then walk the remaining segments to the final type.

crate / self / super — normalize the anchor before walking

A leading crate / self / super segment is a path anchor, not a module name — ["crate","runtime","Driver"] must not die on the literal crate segment, so each anchor is resolved to a crate or module root first.

anchor normalization anchored root scope type bound, constructor resolved

Collision safety — the prefix is the guard, enforced not assumed

When two in-scope modules expose a same-named type each with a new, the path_prefix selects the correct one; ambiguity is evaluated in scope, not via a global name scan, because the single-valued by_scope map collapses same-name bindings.

collapsed same-name binding (unsound to trust) prefix selects the right type
riskiest part — detect collisions in the walk itself (AC #3)

Path-prefix resolution must detect its own collisions rather than trust the collapsed by_scope map's last-write-wins. Same-crate alias hops (use ll::Semaphore, type/cfg aliases) ride this path only when the leading segment resolves through a use/type alias in the same crate; a cross-file re-export hop is import_resolution — bail rather than fabricate an edge.
