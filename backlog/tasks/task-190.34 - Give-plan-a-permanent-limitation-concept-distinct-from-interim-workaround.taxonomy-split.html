Self-repair pipeline · plan taxonomy

Splitting one boolean into the two outcomes it silently conflates

The plan stage marks a group with is_classifier_work — a boolean framed everywhere as an interim workaround with a durable core fix still pending. A permanent limitation with no possible core fix has no cell in that model.

This task replaces the boolean with a tri-state signal so plan represents both disjoint outcomes and prioritize step 3a routes on data, not a bare human eyeball.

Why the boolean is not just under-specified — it is biased backward

The registry (classifier-lifecycle.md) holds classifiers only for permanent limitations; fixable bugs live in backlog/. Yet the strategist prompt's pinned H2 is titled "The classifier is the interim mitigation" and asserts "the core fix is the durable deliverable" — so a strategist following it literally would never surface a pure permanent-limitation group. Plan's model points the opposite way from the regime it feeds.

02The two outcomes land in different places

The split matters because each value has a distinct destination and a distinct owner: an interim workaround graduates to a backlog/ task; a permanent limitation routes to classifier-author and becomes a registry entry — it never files a backlog fix.

permanent path → registry, never backlog interim path → backlog, medium priority core-fix path → backlog, high priority
The routing that becomes data-driven

Today step 3a says the flag "spans two disjoint outcomes" and defers wholly to a human — plan supplies zero positive signal. After this task, step 3a starts from classifier_work === "permanent-limitation" and the human confirms, rather than sorting every --priority classifier group from scratch.

The backstops stay: a fixable bug misrouted to classifier-author still hits its "if fixable, stop" gate; a true limitation misrouted to refactor-investigator still returns its PERMANENT-LIMITATION verdict. The signal makes the common case cheap; the gates keep it safe.

05The one open design decision — the field's name and shape

The plan is settled except for one call: how to encode the tri-state. The string union is the recommended default; two alternatives are on the table.

1 tri-state string union recommended

classifier_work:
"none" | "interim-workaround" | "permanent-limitation"

One field, three named literals. Shape check is a set-membership test; the value reads directly as the routing key at step 3a. Minimal surface, self-documenting, mirrors the classifier.kind union already used in the registry.

2 renamed field alt

fix_outlook:
"fixable-now" | "fixable-later" | "unfixable"

Frames the axis as the fix outlook rather than "classifier work," which reads more naturally at the routing site. Same three-way shape; the trade is a larger rename churn across the ~11 test files and both prompt docs.

3 nested object alt

classifier: { kind, … }

Room to carry per-kind metadata later (e.g. a limitation's static-boundary note). Heavier now, and YAGNI against the constitution — no consumer needs a second field yet, so it adds shape surface with no current caller.

A sub-decision the recommended option forces

Does a permanent-limitation row export to backlog/ at all? Per the lifecycle it routes to classifier-author → registry, not backlog — so select_exportable_tasks likely excludes permanent rows, and only none and interim-workaround produce a backlog/ task.

to decide: field name/shape · whether permanent exports to backlog
The one idea to hold

The registry is the permanent-limitations catalog; the backlog is the fixable-bugs queue. Plan today has a single boolean that cannot tell them apart and a prompt that biases toward "a fix always exists."

This task gives plan a first-class signal for both, so the split the pipeline runs on is carried by data end-to-end — the human stays the final adjudicator, but no longer the only place the distinction lives.
