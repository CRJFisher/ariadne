Self-repair pipeline · classifier catalog

One shape for every classifier: the kind tag is gone

The registry catalogs call relationships that static analysis can never resolve — a callback dispatched through a computed key, a function reached only through a macro. Each entry carries a small classifier that recognizes the pattern. That classifier used to be tagged with a kind that could be one of three things: none (a stub with no check), builtin (a real check function), or retired (a fixed bug's former check, kept for the record). In practice the catalog was one thing: 18 of the 19 entries were builtins, one was an inert stub, and none were retired. This work removed the tag: every classifier is now a plain check — a function name and a confidence threshold — so the code no longer branches on a distinction that stopped distinguishing anything. The lone stub became a firing check, and all 19 rows are permanent builtins.

03Retirement flipped from mark-in-place to delete-the-row

This was the one genuinely subtle change. The retired kind existed on purpose so a fixed bug's from.function_name would not dangle after its check_*.ts was deleted. Removing the kind means a fixed classifier can no longer linger — so name-mode retirement now deletes the row and its check file outright, with git history as the audit trail. The proposal kind is delete_by_name (interface DeleteByNameProposal); it deletes rows of any status (a permanent target is the common case) and best-effort unlinks each row's check_<group_id>.ts.

Why this is the delicate part

The retired kind existed to solve the dangling-name problem: once a fix lands and its check_*.ts is deleted, the row's function_name points at a missing file.

So retired parked the former spec in from on a non-firing fixed row. Deleting the variant re-opens that problem — and the answer is to delete the row too: no lingering row, no name left to dangle.

The fixed status then becomes largely vestigial (a fixed bug is an absent row) — a follow-on, out of scope here.

As-built mechanics · who deletes what, in order

Agent, code-side, first. The retiring agent deletes the builtin's check_<group_id>.ts and removes its barrel import + BUILTIN_CHECKS entry, then rebuilds core. This ordering is enforced: name-mode rejects a row whose function_name is still registered in BUILTIN_CHECKS (surfaced in the summary's rejected_deletions), so the row cannot be deleted while a live check still imports it.

Script, registry-side, second. After the registry write, the run sweeps the named ids' check_<group_id>.ts files — including ids already absent from the registry (the missing_ids set) — as a backstop, then resyncs the permanent slice on every name-mode run (mirroring --promote's unconditional resync). So a crash between the registry write and the cleanup is recovered simply by re-running. The unlink dep is build_delete_builtin_source(builtins_dir), testable against a temp dir; the summary reports what it removed in deleted_builtin_sources.

The --reason text is not persisted on any row — it survives only in the run summary and the human's commit message. Git history is the audit trail.

06What is traded, and what is bought

The accepted trade

Given up: the in-registry, lossless retirement audit — a fixed bug's former from spec and reason preserved on a durable fixed row.

Bought: a type with one shape instead of three, five files that stopped asking “which kind?”, and a catalog where every entry carries a real, firing check — including the lambda-handler row that was dead weight.

The retirement record moved from the registry to git history: the --reason text lives only in the run summary and the commit that deletes a row, which is the audit trail. Accepted per the task request.
