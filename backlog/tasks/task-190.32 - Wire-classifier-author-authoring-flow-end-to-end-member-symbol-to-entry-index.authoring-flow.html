01The broken link, and where the bridge goes

CURRENT: prioritize holds only member_symbol + run_id, but get_entry_context.ts accepts only the run-local entry_index — the flow stalls at the first hop. PLANNED: the script gains a stable selector and resolves the entry itself.

added surface modified stalled / failing edge unchanged
Why it stalls today

The data prioritize holds (member_symbol) is not what get_entry_context.ts accepts (entry_index), and nothing documents the translation.

Compounding it, prioritize/SKILL.md step 3a has no dispatch-prompt template — unlike every sibling step — so an orchestrator has neither the data nor the instruction to build a valid dispatch.

02Why the two keys don't meet — and why the bridge is trivial

The four stable fields are already present in each TriageEntry, so resolving member_symbol → entry is a direct .find() field match — no new data, no new store.

03Two fix options — keep the stable identity, or re-thread the unstable index

Both make the flow work; they differ in which component is forced to handle the drift-unstable index.

1 OPTION 1 recommended

Extend get_entry_context.ts with a stable selector

Add --member-symbol (+ --run-id); the script resolves member_symbol → entry internally against the run's triage state. Prioritize keeps the stable identity and never touches the unstable index. The drift-fragile translation lives in exactly one place, right next to the state file it reads.

2 OPTION 2 rejected

Thread entry_index through prioritize

Pair each plan group back to its source NovelIssue per run_id at dispatch time to recover the index. Re-introduces the exact index the plan engine deliberately dropped for being line-drift unstable — prioritize now owns a fragile positional key across sweep boundaries.

Recommendation

Take Option 1. The classifier-author tools grant already prefix-matches get_entry_context.ts:*, so new flags stay permitted with no agent-config change; the four identity fields already live in TriageEntry, so the resolver is a one-line .find().

Open sub-decision · not yet decided

How the stable selector is encoded on the CLI is genuinely open. (a) one packed argument — --member-symbol '{"file_path":…,"name":…,"kind":…,"start_line":…}' (JSON or a delimited string): one flag, but the caller must serialize/quote it. (b) four discrete flags — --file … --name … --kind … --line …: no quoting, but four values to keep aligned. Both round-trip the same four fields; pick during implementation.

decide in: get_entry_context.ts parse_args + the step-3a template that emits it

04The full flow, once Option 1 lands

Five hops, each owned by a named actor — prioritize never handles an index, and the human still owns the registry write at the end.

05The routing false-negative — an asymmetric gap

One misrouting is caught; its mirror is not. A fixable bug sent to classifier-author hits the agent's "if fixable, stop" gate — but a true permanent limitation sent to refactor-investigator → backlog has no symmetric backstop, so the limitation silently never gets its classifier.

Acceptance latitude

AC-4 is satisfied either by addressing the gap (mitigation a or b) or by explicitly documenting it as accepted — the decision itself must be recorded, not left implicit.
