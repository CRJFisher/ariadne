Name-mode — human names the rules directly

Where name-mode sits among the selectors

Name-mode is additive: it mirrors --id --promote (names rules, bypasses detection) but writes fixed instead of permanent. The auto --fixed path (no --id) is unchanged.

Invocation Detects via git log? Names rules directly? Clears classifier? Writes
--fixed (no --id) ● yes ○ no ○ no — status only wip → fixed
--id … --fixed new ○ no — bypassed ● yes ● yes — → none wip → fixed + classifier → none
--drift ◑ published runs ○ no ○ no drift_detected: true + evidence
--id (selector) ● scans both ◑ narrows ○ no only named rules' detected proposals
--id … --promote ○ no — bypassed ● yes ○ no — requires classifier wip → permanent + sync slice

The mirror: name-mode copies --promote's shape — a per-id branch in run() that takes --id rules directly, with unknown id → missing_ids and a non-wip named rule a silent no-op.

The key decision — name-mode also clears the classifier

AC #3 · decided

Name-mode flips status and sets the rule's classifier to {kind:"none"} in the same atomic_update_registry transaction. One sanctioned command closes the whole retirement — exactly the two registry edits TASK-348.2 made by hand.

Why clearing is required, not optional

A fixed rule is dropped from classification entirely (active_rules_for_classification excludes fixed), so its classifier is permanently inert.

Worse, a retired kind:"builtin" rule whose implementation file is deleted is a dangling reference: the auto-generated BUILTIN_CHECKS barrel imports each builtin by name, so a deleted file breaks compilation.

The asymmetry — and why it is justified

The auto-detected --fixed path stays status-only: a mechanical stamp reacting to a landed commit, with no signal that an implementation file is being removed.

Name-mode is the human deliberately naming rules to retire, so clearing the classifier there is the safe, intended bundling.

The name-mode branch

A new proposal kind wip_to_fixed_by_name; in run(), when --fixed accompanies --id, take a name-mode branch that bypasses the fixed-signal detector. The write still flows through the single atomic_update_registry transaction.

// A direct, human-named retirement — no git-log backlog_task matching.
export interface FixedByNameProposal {

  group_id: string;
}
reconcile_registry.ts — run(): name-mode branch (mirrors --promote) 
if (args.fixed && args.ids.length > 0) {
  // Name-mode: bypass detection entirely, mirror --promote's shape.
  for (const id of args.ids) {
    const rule = rules_by_id.get(id);
    if (rule === undefined) {
      missing_ids.push(id);              // unknown id → reported
    } else if (rule.status === "wip") {
      fixed_by_name_proposals.push({ kind: "wip_to_fixed_by_name", group_id: id });
    }                                    // non-wip named rule → silent no-op
  }
}
reconcile_registry.ts — fold_proposals(): status AND classifier, one transaction 
case "wip_to_fixed_by_name":
  if (rule.status === "wip") {
    next[i] = { ...rule, status: "fixed", classifier: { kind: "none" } };
  }
  break;

Permissions — no broad allow-rule

Part C · decided

Do not add a broad Bash allow-rule for registry writes — it would weaken the self-modification safeguard the classifier enforces (.claude/rules/hook-errors.md).

The name-mode plus the printed one-liner reduce the human's manual run to a single command — the accepted cost of keeping the human the literal writer of registry.json.
