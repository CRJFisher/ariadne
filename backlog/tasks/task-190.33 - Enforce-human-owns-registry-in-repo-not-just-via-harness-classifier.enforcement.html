Classifier registry · in-repo enforcement

Making "the human owns the registry" true in the repo, not just in the harness

The classifier registry is the loop-closure surface: every status transition is a human decision. Three places in classifier-lifecycle.md claim a mechanical guard blocks an agent from writing it — but nothing in the repository enforces that.

A PreToolUse hook that routes every agent write of registry.json to a per-edit human ask puts the guard back inside the repo, where it survives a harness change.

What the doc claims vs. what actually enforces

The current guard rests entirely on an out-of-repo harness classifier that is probabilistic in practice — during TASK-190.30.2 the first several edits to the registry succeeded before it flagged a later one. The fix adds an in-repo layer and demotes the harness to defense-in-depth.

The three claims the doc makes — none backed by repo config

.claude/settings.json has empty deny and ask lists; its only PreToolUse hook is the file-naming validator (matcher Write|Edit). The registry_writers.test.ts AST-walk catches lock-bypassing code at build time — it does not stop an agent hand-editing the JSON via Write/Edit.

How the hook decides — and where the Bash heuristic lives

The hook follows the existing pattern: read stdin JSON via parse_stdin(), resolve the target, emit hookSpecificOutput. Write/Edit resolve cleanly from tool_input.file_path; Bash is the hard case — the command string must be inspected, but a read-only cat/grep/jq of the registry should not prompt.

ask — the per-edit human checkpoint Bash heuristic — the real decision point unattended → deny (headless resolves ask to deny)
The one design choice this hook makes

Prompting on every mention of registry.json would nag on read-only cat/grep/jq and on the sanctioned human path (reconcile_registry.ts, writing under the registry.json.lock sidecar).

Prompting only on a write-indicator keeps the ask targeted; a redirection or unusual write form that slips past is still backstopped by the harness classifier.

The secondary fix: closing the --promote membership hole

run_stage already rejects a builtin whose function_name is absent from core's BUILTIN_CHECKS (step 5). The --promote branch checks classifier.kind and already-permanent, but never re-checks membership — so a builtin whose check_*.ts was deleted after staging could be promoted and leave the slice referencing a dangling name.

The ReconcileDeps.known_builtin_names() thunk already exists and is used by run_stage — the fix reuses it, keeping the authoring boundary and the promotion boundary enforcing the same invariant.

Why this matters to the pipeline

The registry is where the self-healing loop closes: a landed fix flips a classifier wip → fixed. If an unattended agent could rewrite it, the human-owned loop-closure surface becomes agent-writable.

This task makes that ownership enforced by the repo itself — so it holds even if the out-of-repo harness feature is off or changed.
