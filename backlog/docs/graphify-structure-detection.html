Graphify · structure detection

Two lanes, one graph

Graphify detects structure with two independent pipelines that never look at the same file. Tree-sitter reads the code. An LLM reads everything that is not code. They meet once, at the merge, and from there the graph is a single artifact on disk.

The whole run

One command, ten stages

The split happens early and by file type alone. A .py file can only ever go down the tree-sitter lane; a .md file can only ever go to the model. This is why a code-only repository needs no API key at all, and why the LLM can never fix a parser gap.

Everything above happens inside a single CLI command. The report, the community names and the HTML view are a second command — extract deliberately stops at the graph.

AST lane — per file

Dispatch, then a two-pass walk

Each file is routed to exactly one extractor. Routing is by extension, except where an extension is genuinely ambiguous — then Graphify reads the file and decides, and if it still cannot tell, it parses nothing rather than mangling the file through the wrong grammar.

Not one tree-sitter query in the repository

There is no .scm file and no call to the Query API anywhere in Graphify. Every construct is found by a recursive Python walk comparing node.type against frozensets — roughly 791 such comparison and field-lookup sites. Adding a mainstream language costs about fifteen lines of configuration; changing what a language extracts means editing control flow inside a 4,747-line function.

AST lane — whole corpus

Where an edge lives or dies

Once every file is extracted, the parked raw_calls are resolved against a corpus-wide name index. Graphify's rule is that a name match alone is not evidence: an ambiguous call produces no edge at all rather than a guessed one. Follow the rust-coloured paths to see everything that silently disappears.

Six ways an edge disappears, none of them recorded

Every failure path above is a bare continue. Nothing keeps the call site, the callee name, or the reason. A user can read the aggregate confidence line in the report — what share of edges are guesses — but can never ask why one specific function ended up with no callers. The answer existed, and was thrown away at the moment it was known.

Agentic lane

The model reads everything except the code

Documents, papers and images go to an LLM, which returns nodes and edges in the same id format the AST extractor uses — that shared recipe is why the two lanes can be merged at all. The cache here is keyed on a fingerprint of the exact prompt rather than the package version, because invalidating on every release would re-bill the user.

The lanes are a partition, not two views

No source file is ever seen by both. The model cannot rescue a construct the walker missed, and the walker never reads a design document. What the merge combines is a code graph and a document graph that happen to mint compatible ids — and where those ids collide, the model's node overwrites the parser's.

Side by side

What each lane owns

Lane Reads Produces Cache key Failure mode
AST Source files, one at a time, by extension and content sniffing File, class and function nodes; contains, method, calls, imports and indirect_call edges Package version plus file hash — a release invalidates it Silent. Ambiguous calls vanish with no record of the attempt
Agentic Documents, papers and images, packed into chunks by directory Concept and document nodes, cross-file edges, hyperedges that nothing reads Prompt fingerprint plus file hash — a release must not re-bill Loud. Zero successful chunks exits; partial success arms the shrink guard

Both lanes reach the same undirected NetworkX graph, written atomically to graphify-out/graph.json. Direction survives only as a pair of edge attributes that a NetworkX round-trip destroys — which is why the incremental merge path reads the raw JSON instead.
