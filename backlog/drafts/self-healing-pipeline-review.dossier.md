## 1. Executive summary

The pipeline's core architecture is genuinely strong. Its best disciplines are consistently applied and were affirmed by multiple lenses: pass-by-reference hand-offs at every wave boundary with terse or empty text returns (`triage-investigator.md:91`, `plan-strategist.md:247`, `refactor-investigator.md:129-130`); file-authoritative verdicts (`triage/SKILL.md:208` "Ignore its `<result>` body entirely"); single-producer artifacts and append-only run stores; deterministic-first ordering (registry builtins classify before any LLM dispatch, `triage/SKILL.md:166`); a fail-closed export adapter (`export_to_backlog.ts:198-204` refuses to write without `--assignments`); and a registry write path that is triple-enforced (lock-sidecar `atomic_update_registry`, AST-walk test `registry_writers.test.ts:277`, and the `PreToolUse` guard hook). The finalize guard in plan is exemplary: a half-finished sweep can only _block_ retirement, never cause spurious resolution (`load_staged_plans.ts:149-156`, `reconcile_plan.ts:67-92`).

The risk posture, however, is asymmetric: **the safety properties the docs advertise most loudly are the ones with the weakest enforcement.** Five themes dominate:

1. **The human-ownership boundary is enforced lexically and by prose, not structurally.** The registry guard's decision function is well tested, but its enforcement seam (hook wrapper + settings matcher) has zero coverage, standing `python3`/`node` allow-rules under `acceptEdits` route around its token list entirely, and the analogous "only writer of backlog/" claim is simply false with no hook, test, or allowlist behind it.
2. **Judge outputs gate irreversible decisions with only shape-level checks.** `consolidation.json` (the "spine of the run") has no validator at all; a strategist's `belongs: false` permanently suppresses an FP with no correctness re-check; the architect's "tests cover every evidence case" invariant and classifier-author's field-subset rule are prose-only; a drafted classifier is never executed against its own samples before registry insertion.
3. **Doc-vs-code drift on load-bearing contracts.** plan's SKILL.md documents an export invocation the code hard-refuses; prioritize claims a gitignore rule that does not exist; the only meta.json in the pipeline (plan's) declares a registry read the skill forswears.
4. **Crash-recovery and write-atomicity discipline was applied only to the registry.** triage's shared state file is a bare `writeFileSync` guarded by prose; plan sweeps and prioritize runs cannot resume; the task-DB has no interlock between its two writers.
5. **The loop-closure identity (`dedup_key`) is line-drift-unstable**, so any target-repo commit can resurface already-funded work as fresh proposals — the one cache leak the pipeline does not document.

Nothing here indicates an unsound design; most fixes are small-to-medium and additive (a validator script, a lock, a test for the guard seam, doc corrections). The one operational blocker found live: a stale pre-190.35 task-DB row (`~/.ariadne/plan/tasks/pt-018de0f069fbfd82.json`) currently aborts even `--dry-run` exports and will block the next prioritize run until reconciled.
