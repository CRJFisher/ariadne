export_to_backlog — the one place the firewall is crossed

The plan engine writes only to its own task-DB at ~/.ariadne/plan/. This adapter is the single sanctioned bridge that promotes selected DB rows into the user's backlog/tasks/*.md. It is the human's control gate and the portability seam: a different tracker target is a second adapter, with no engine or DB change.

The data flow

Five steps from a proposed DB row to an idempotent no-op on re-run. The stamp at step 3 is the only durable side-effect a later sweep reads back.

select / write creates / flips (olive = done) loop-closure read-back (later sweep)
1
Select — query the DB by --status (default proposed), --fault-area, the --priority selector (see Decision 1), or explicit --id. --dry-run prints the selection and writes nothing.
2
Wrap — each PlanTask's already-rendered title + body drop into the backlog file format (frontmatter + ## Description / ## Acceptance Criteria sections). No re-render (see Decision 3).
3
Stamp — write plan_dedup_key: <PlanTask.dedup_key> verbatim into frontmatter, plus the source DB id for traceability. This field is a fixed contract — never renamed or transformed.
4
Flip — on success, move the DB row proposed → exported and record exported_backlog_task = the minted backlog id. Append an export PlanSweepEvent.
5
Idempotent re-run — a row already exported with a matching id is skipped: no duplicate backlog task. Same no-op-on-match guard as the retired link_ariadne_bug_tasks.
The loop closes at step 3

A later sweep's reconciler (backlog_dedup.ts) reads plan_dedup_key back from every backlog file and maps it to that file's id. A DB task whose dedup_key matches is marked exported and suppressed — the engine stops re-proposing work the human already promoted. The stamp is the entire contract between writer and reader; nothing else is shared.

Decision 3 — "reuse render_task_*" means wrap, not re-render

The scope says the adapter "reuses the pure render_task_* row-builders." This is easy to misread. Those builders take a StrategistPlanNode — and the adapter has no node. It has a PlanTask whose title and body are already the output of render_task_title / render_task_body, run once by the engine when the row was minted.

Do not

The adapter does not reconstruct a StrategistPlanNode and call the renderers again. There is no node to reconstruct, and re-rendering could drift from what the engine already committed — and from what the dedup_key was computed against.

Do

The adapter wraps the stored PlanTask.title and PlanTask.body into the backlog file envelope (frontmatter + section markers). The renderers are "reused" in the sense that their output flows through unchanged — the pipeline already paid that cost upstream. The adapter's job is format translation, not content generation.

the wrap, in essence — no node, no re-render
function to_backlog_file(task: PlanTask, backlog_id: string): string {
  const frontmatter = render_frontmatter({
    id: backlog_id,
    title: task.title,            // already [area]-prefixed by render_task_title
    priority: task.is_classifier_work ? "low" : "high",
    plan_dedup_key: task.dedup_key,   // verbatim — the loop-closure contract
    plan_source_task: task.id,
  });
  return frontmatter + "\n## Description\n"
    + SECTION_BEGIN + task.body + SECTION_END;   // body flows through unchanged
}
