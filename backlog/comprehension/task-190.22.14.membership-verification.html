TASK-190.22.14 · self-repair / plan-strategist / membership

The strategist verifies who really belongs in a bucket

Pass A buckets every false-positive by a deterministic lookup, and that lookup can mis-route a member into a group whose root cause it does not share. Before the strategist plans a fix, it now reviews each member it was handed — confirming the genuine ones and excluding the outliers — so a fix is only ever grounded on evidence that shares its root cause, and the exclusion is recorded across the stores so it is never silently lost nor re-litigated every sweep.

Why a mis-route corrupts the evidence and the dedup_key

Pass A (group_fault_areas) is pure and total: it flattens every published false-positive, runs each through derive_fault_area — a deterministic lookup over diagnosis + (stage, reason) — and drops it into the bucket for that AriadneFaultArea. Cheap and stable, but it has no judgement. A borderline (stage, reason), a defaulted derivation (needs_judgement: true), or a genuinely cross-area fault can land a member in a bucket whose bulk root cause it does not actually share.

Today the strategist must plan over every member it receives. So a mis-routed member is baked in three places at once, each downstream of the last:

Where the mis-route landsThe corruption
node.evidence_indicesThe strategist grounds a node on a member that belongs to a different fault — the prose and the fix target a root cause that member doesn't have.
aggregated evidence (up the tree)build_plan_tasks unions a node's evidence with every descendant's, so the stray member propagates into the parent's evidence and rollup (observed_count, projects).
PlanTask.dedup_keyThe key is a hash of fault_area + the sorted set of call-site file:line tokens. A stray member changes that set, so the task reconciles as a different task across sweeps — the augment-not-duplicate guarantee silently breaks.
The one stage with judgement

The strategist is the only pass that holds Read/Grep/Glob and can actually read the code. So before it plans, it verifies the members it received: for each one it confirms belongs (shares the group's bulk root cause) or does-not-belong, with a reason and — when it can tell — the area the member should route to instead. A rejected member never enters a node, so it never reaches the aggregated evidence or the dedup_key.

The three passes, with the membership review overlaid

Pass A groups, Pass B (the strategist) plans, Pass C reconciles into the task-DB. The new review sits at the front of Pass B and threads its consequences through Pass C and back into a future Pass A.

The verdict shape and what the validator enforces

The verdicts live as a first-class array on the strategist's output, keyed positionally to the same evidence[] index space the nodes reference. One verdict per index, no gaps — that totality is exactly what lets the validator catch an unreviewed member.

export interface MembershipVerdict {

Member identity — the key, riskiest decision (AC#4)

The override store must key on a member identity that survives line drift: a member excluded this sweep must be recognisable as the same member next sweep, even after edits shift its line. AC#3 names "key the override on symbol identity, not file:line." The faithful realization of that runs into a hard constraint in the current pipeline.

Critical finding

A true branded SymbolId — grammar kind:file:start_line:start_col:end_line:end_col:name — is not constructible anywhere on this path. Core's EnrichedEntryPoint, triage's TriageEntry, and EntryPointDiagnostics all carry only (name, file_path, start_line, kind) — never columns, never end-line. The finalize step builds each published row's member_symbol from exactly that tuple (output.ts reads entry.{name, file_path, start_line, kind} via entry_ref). So "thread a real SymbolId" cannot be honored as written.

The faithful realization is therefore the flagged entry point's coordinate identity: a structured tuple, not the call-site file:line token. This is the same tuple triage's TP-cache already uses as its stable cross-machine match key.

the chosen identity — a structured tuple, keyed canonically in one place
export interface MemberSymbol {
  file_path: string;   // relative to project_path (stable across machines)
  name: string;
  kind: "function" | "method" | "constructor";
  start_line: number;
}

// one canonical recipe, analogous to location_token() — lives in ONE place.
// Joins the MemberSymbol fields in DECLARATION order, newline-delimited so
// no value can collide with the delimiter (twin of location_token's discipline,
// but over the FLAGGED MEMBER's four-field tuple rather than the call site).
export function member_identity_token(m: MemberSymbol): string {
  return [m.file_path, m.name, m.kind, String(m.start_line)].join("\n");
}

Two distinct identity primitives — don't conflate them

The dedup_key and the member identity are deliberately separate primitives, and this task touches only the second. dedup_key is unchanged: a hash of fault_area + the sorted set of call-site file:line tokens, used for exact-overlap task reconciliation (does this sweep's task cover the same call sites as a stored one — augment, don't duplicate). member_identity_token is new: it identifies a single flagged member by its coordinate tuple, used for routing (which bucket should this one member go in next sweep). One keys a task by its call sites; the other keys a member by its symbol. They answer different questions and never share a recipe.

The drift caveat, stated honestly

(file_path, name, kind) is the drift-tolerant core. start_line is the collision-breaker for same-name / overload cases — and it still drifts when surrounding edits move the symbol. So MemberSymbol is line-drift-resilient, not line-drift-immune: a rename, a move across files, or a same-file edit that shifts the start line lets a member re-enter the review and acquire a fresh override. The store and its token are documented with this honest caveat, not as "line-drift-stable."

True line-drift immunity needs symbol-graph identity from core — the separately-coupled "dedup_key symbol-identity hardening" work, which is not yet a task. This task delivers the best identity the current rows can express, and names the gap rather than papering over it.

Why "exclude this sweep only" is not enough

Every sweep re-buckets via derive_fault_area from scratch. A sweep-local exclusion would re-route the same member into the same wrong bucket next sweep, and the strategist would re-reject it forever. The persistent override is what stops the re-litigation; the correction signal is what eventually removes the need for it.

The derive_fault_area correction signal (AC#4)

A confirmed mis-route — an exclusion carrying a suggested_area — means derive_fault_area systematically mis-routes that signal. Reconcile surfaces those as a derive_fault_area_corrections[] rollup in its summary: each entry { from_area, to_area, member, reason }. This is the human-readable signal to fix the derivation or extend the taxonomy — the same spirit as the existing other-bucket taxonomy-extension path. No separate PlanTask is minted for it (YAGNI): the systematic fix lands in the taxonomy, not in a per-member ticket.

Write-boundary preserved (AC#5)

The strategist writes only its plan JSON · reconcile is the sole writer of the task-DB and the override store · Pass A only reads the override store · no new tool grant — the strategist already holds Read/Grep/Glob. The plan engine still makes zero writes to backlog/, registry.json, or packages/core.

What to watch

!
Ping-pong re-routing across sweeps — re-routing is a single step from the derived area, and the validator forbids a suggested_area equal to the bucket's own area, so a member can't be sent straight back where it was excluded. But a suggested_area that points at a third bucket whose strategist then re-rejects it is a fresh mis-route the strategist reviews again. The override store dampens this (an override at the destination suppresses rather than re-routes); the test to keep is that a re-sweep does not re-emit an exclude_member event for an already-recorded member.
!
start_line drift — an edit that shifts a flagged symbol's start line changes its member_identity_token, so its override stops matching and the member re-enters the review once. This is expected and bounded (one re-review, then a fresh override), but it is the concrete cost of not having true symbol-graph identity — the reason the drift caveat is load-bearing, not a footnote.
!
Suppression persists until a human clears it — an override with no suggested_area suppresses the member unconditionally and indefinitely. Unlike the classifier registry's resurfaced-fixed-row review, a suppressed member that genuinely resurfaces in a later run is silently dropped; clearing the entry from membership_overrides.json is the recovery path.
Verification — the acceptance checklist

A plan excluding a mis-routed member produces PlanTask rows whose evidence and dedup_key omit it · an exclude_member PlanSweepEvent records the exclusion · the member is written to membership_overrides.json · validate_plan rejects an unreviewed index, a node grounding an excluded index, and a suggested_area equal to the bucket's own area · a confirmed mis-route is also surfaced positively (the AC#3 positive test) · an end-to-end loop test confirms exclude → store → next-sweep re-route · the plan engine makes zero writes to backlog/, registry.json, or packages/core.
