TASK-190.22 · self-repair / architecture / restructure

The self-healing pipeline becomes two stages: detect, then plan

The pipeline under .claude/skills/ has never run end-to-end. Rather than building the full automated build-out at once, the architecture collapses to the part that delivers value first — and keeps code mutation a manual, human-driven step. There are two live stages; fix delivery is manual and out of scope.

What the pipeline is for

Two golden-path stages run autonomously; the third is a deferred draft. The boundary between "the machine proposes" and "code or the user's tracker changes" is the whole point of the restructure — autonomous stages never mutate code, the classifier registry, or the user's backlog.

stage 1 · golden path

triage

Detect entry points → per-entry investigator verdicts (tp = real dead code, fp-* = an Ariadne resolver bug) → publish triage_results, each false-positive carrying deterministic core fault diagnostics.

stage 2 · golden path

plan

Read all triage_results → group by AriadneFaultArea → opus strategists propose architectural upgrades → emit hierarchical, size-tiered fix plans into the task-DB → reconcile (augment / supersede / combine). Produces plans; never mutates code or the registry.

manual · out of scope

fix delivery

Out of scope. The human executes the plans by hand: path A = localized Ariadne-core fixes, path B = classifier-script fixes. Code mutation, registry maintenance, and loop-closure are all manual, human-driven steps.

The two write boundaries that hold the shape

Both autonomous stages are read-only against two human/core-owned surfaces. The classifier registry (registry.json) and the user's backlog/ each have exactly one named writer per transition; an AST test fails the build if pipeline code writes the registry, and the backlog is written only by the export adapter. The plan engine renders proposed work into its own task-DB at ~/.ariadne/plan/; a single human-invoked adapter is the sole bridge from there into backlog/.

How the sub-tasks compose into the whole

The work moves left to right: harden the detector, extract the shared contract and taxonomy, stand up the task-DB and its write-boundary, build the plan engine on top, then open the one sanctioned gate out to the user's tracker. The diagram groups the thirteen sub-tasks by the layer they build.

Where the family stands

The detector, the shared @ariadnejs/skill-protocol contract, the AriadneFaultArea taxonomy, the JSON task-store, both write boundaries, and the full plan engine (group → strategize → reconcile within the DB) are all landed. What remains is the human-facing edge: the export gate that promotes DB rows into the backlog (.11), migrating the 234 auto-filed classifier tickets into the DB (.12), and giving the strategist a feasibility judgement to abandon intractable plans (.13).
