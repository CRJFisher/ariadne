Membership convergence holes in the plan pipeline

status To Do parent 190.22 labels self-repair · bug parallel with .15 (trivial merge at load_staged_plans)
What this task fixes Two holes in the 190.22.14 membership-verification work defeat its own convergence goal — that a membership decision, once made, prevents re-adjudication on subsequent sweeps. Without these fixes, excluded members loop back into the same bucket every sweep and are re-excluded indefinitely. Membership override records are also keyed on the wrong area, making the convergence guard bypassable.

Hole 1 — Two-hop re-adjudication loop

1

Override lookup keyed on the derived area only — re-routed destination never consulted

Location: .claude/skills/plan/src/group/group_fault_areas.ts ~line 101

group_fault_areas consults the override store keyed (derived_area, member). When an override is found with a suggested_area, the member is re-routed into that destination bucket. No second lookup is performed for the destination area.

The failing scenario

Sweep 1:
  member derives to area A
  no override for (A, member) → lands in A's bucket
  A's strategist: belongs=false, suggested_area=B
  record_membership_decisions writes override (A, member) → B

Sweep 2:
  member again derives to area A
  override found: (A, member) → B, so member re-routes into B
  B's strategist: belongs=false, suggested_area=null (suppress)
  record_membership_decisions writes override (B, member) → null

Sweep 3:
  member again derives to area A
  override found: (A, member) → B ← only one lookup
  override (B, member) → null is NEVER consulted
  member lands in B's bucket and is re-excluded — forever

The 190.22.14 convergence guard in validate_plan (issue code membership_suggested_area_is_own_bucket) only blocks self-routing (A → A), not this two-hop loop.

Fix

After re-routing via an override's suggested_area, perform a second override lookup keyed on (destination_area, member) before bucketing. Follow the chain with a cycle guard (detect A → B → A by tracking visited areas). A suppressed member at any hop in the chain is discarded. The chain length in practice is at most two or three hops, so simple visited-set tracking suffices. Cover the derive → override → exclude → next-sweep loop in group_fault_areas.test.ts, including the cycle case.

Hole 2 — Plan identity never cross-checked against the dispatched bucket

2

validate_plan checks fault_area is in the taxonomy but not that it matches the dispatched bucket's area or sweep

Location: .claude/skills/plan/src/propose/validate_plan.ts ~line 315–320 and src/reconcile/record_membership_decisions.ts ~line 64

StrategistPlan is documented as self-contained — it carries fault_area and sweep_id "so the validator and reconcile engine cross-check against the bucket fed to them." validate_plan verifies only that fault_area is a valid taxonomy member and sweep_id is non-empty. Neither is compared to the dispatched bucket even though ValidatePlanContext already carries bucket_fault_area.

Consequence — miskeyed exclusions + bypassable convergence guard

// record_membership_decisions.ts ~line 64 — keyed on plan.fault_area, not bucket.fault_area:
return {
  fault_area: plan.fault_area,   // ← wrong when plan.fault_area ≠ bucket.fault_area
  member: evidence.member_symbol,
  reason: verdict.reason,
  suggested_area: verdict.suggested_area ?? null,
};

// validate_plan.ts — membership_suggested_area_is_own_bucket guard
// checks against bucket.fault_area while the exclusion is written under plan.fault_area
// → guard fires on plan.fault_area === bucket_fault_area, bypass by setting them unequal

A strategist that writes fault_area: "X" into plans/Y.json (where Y's bucket area is Y) passes validation today. Its exclusions are recorded under X, making them dead for bucket Y — the member is re-adjudicated every sweep — and wrongly suppressing or re-routing any future member whose derived area is X.

Fix

Extend ValidatePlanContext with bucket_sweep_id: string. In validate_plan, add two new issue codes: fault_area_mismatch (plan's top-level fault_area does not equal ctx.bucket_fault_area) and sweep_id_mismatch (plan's sweep_id does not equal ctx.bucket_sweep_id). In load_staged_plans.ts — the call site that builds ValidatePlanContext — pass the dispatched sweep_id as bucket_sweep_id. Cover both rejection paths in validate_plan.test.ts.

Parallel with TASK-190.22.15 Both tasks touch load_staged_plans.ts. TASK-190.22.15 changes the rejected/missing plan accounting; this task adds one field to ValidatePlanContext. The overlap is confined to that file and the merge is trivial — both tasks can proceed in parallel.
