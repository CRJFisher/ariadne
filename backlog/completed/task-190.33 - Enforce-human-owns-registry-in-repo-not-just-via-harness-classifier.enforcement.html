What the guard is wired into — and where its logic lives

.claude/settings.json now carries a second PreToolUse entry, matcher Write|Edit|Bash, running registry_write_guard.ts under node --import tsx, alongside the file-naming validator.

The decision logic and its 26 tests live in .claude/skills/triage/src/ — because .claude/hooks/ sits outside the repo's test/lint/typecheck nets; the hook file is a thin fail-open wrapper.

How the hook decides — two layers, and a hardened Bash heuristic

The .claude/hooks/ entry parses stdin, calls evaluate_tool_call(), and on ask emits the decision JSON before logging so an unwritable log can't swallow it. Write/Edit resolve cleanly; Bash is the hard case, hardened after a live over-trigger.

ask — the per-edit human checkpoint Bash heuristic — bound writes only unattended → deny (headless resolves ask to deny)
The Bash rule the guard settled on (after hardening)

It asks only when a write construct is bound to the registry path within one pipeline segment: a redirect into it, tee/sed -i/perl -i, a command-position-anchored mv/cp/rm/dd/truncate, git checkout/restore, or a writeFileSync-family call — a grep -rm flag cluster is not an rm.

Running reconcile_registry.ts asks only in write-mode: a runner token (node/npx/tsx/pnpm) is required, so a mention passes; a bare invocation writes so it asks; --dry-run/--help/--stage-without---apply pass. Flags are token-matched with quoted segments stripped, so --reason "see --dry-run docs" cannot spoof read-only.

The secondary fix: closing the --promote membership hole

run_stage rejects a builtin whose function_name is absent from BUILTIN_CHECKS; the --promote branch never re-checked membership, so a builtin whose check_*.ts was deleted after staging could promote a dangling name into the slice.

.claude/skills/triage/scripts/reconcile_registry.tsrun() · promote branch ~642-671
// --promote path in run() — membership gate placed BEFORE already-permanent
const rule = rules_by_id.get(id);
if (rule === undefined) {
  missing_ids.push(id);
} else if (rule.classifier.kind === "none" || rule.classifier.kind === "retired") {
  rejected_promotions.push({ group_id: id, reason: `classifier.kind is "…" — author a builtin first` });
// Root-cause defect outranks the benign no-op reason: a deleted check_*.ts is
// checked BEFORE already-permanent so promote can't bundle a dangling name.
} else if (!deps.known_builtin_names().has(rule.classifier.function_name)) {
  rejected_promotions.push({ group_id: id, reason: `function_name not in BUILTIN_CHECKS … then re-promote` });
} else if (rule.status === "permanent") {
  rejected_promotions.push({ group_id: id, reason: "already permanent" });
} else {
  promote_proposals.push({ kind: "promote_to_permanent", group_id: id });
}

The rejection is a rejected_promotions row (not a throw), mirroring run_stage's remediation down to the "re-promote" instruction; the known_builtin_names() thunk is reused, so authoring and promotion enforce one invariant.

Live validation — the guard proved itself, then got hardened

The guard's first version over-triggered: during the build session it raised 43 spurious asks from read-only reviewer commands — mentions of reconcile_registry.ts that weren't executions, and write tokens unbound to the registry path.

That noise empirically proved ask overrides auto-accept; the bound-write / write-mode / quoted-flag-stripping heuristics above are the fix. CI now runs the triage suite, so the guard's 26 tests gate merges.

Why this matters to the pipeline

The registry is where the self-healing loop closes: a landed fix flips a classifier wip → fixed. If an unattended agent could rewrite it, the human-owned loop-closure surface becomes agent-writable.

This task makes that ownership enforced by the repo itself — so it holds even if the out-of-repo harness feature is off or changed.
