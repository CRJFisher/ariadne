TP cache: fall back through older runs at the same commit

status Done priority medium labels self-repair · bug parent TASK-190.22.16
The fix in one sentence

When the most recent run at the current commit has no reusable llm-tp verdicts — because that run was itself a cache-reuse run — derive_tp_cache walks back through older finalized runs at the same commit, reading each file lazily, and stops at the first that yields a non-null cache, instead of giving up and re-investigating everything with the LLM.

The alternating cadence

Each run derives its cache from prior published results at the same commit. build_cache only indexes rows with source.kind === "llm-tp" — a reuse run's output (all previously-confirmed-tp) yields nothing. While derive_tp_cache consulted only the single most recent run, every second run found an empty source and paid the full LLM cost again.

Where it broke

Two pieces interact. The eligibility filter (landed in TASK-190.22.16) is correct and stays: a cache hit is never itself reused, because the published row carries no origin chain. The defect was in run selection — a single lookup that trusted whatever the lex-max run happened to contain.

export async function all_finalized_runs_at_commit(
  project: string,
  short_commit: string,
): Promise<string[]> {   // run-ids only — no file contents are read
  const dir = triage_results_dir(project);
  let files: string[];
  try {
    files = await fs.readdir(dir);
  } catch {
    return [];
  }
  const prefix = `${short_commit}-`;
  return files
    .filter((f) => f.startsWith(prefix) && f.endsWith(".json"))
    .sort()
    .reverse()   // ISO-timestamp suffix ⇒ lex-descending = newest first
    .map((f) => f.slice(0, -".json".length));
}

Lazy by design

The store function returns string[] — run-ids only — so listing candidates costs one readdir and zero file reads. derive_tp_cache reads each candidate on demand and early-exits at the first non-null cache, keeping file I/O proportional to runs actually needed rather than total runs at the commit. In the alternating scenario that is at most two reads: the reuse run (skipped) and the original investigation run (hit).

Known edge

A corrupt or legacy-schema file encountered during the walk throws: the parse error propagates from read_triage_results. This matches the prior single-run behaviour and is an accepted edge — the published store is append-only and schema-validated at write time.

Why this terminates

Within one commit there is at most a handful of finalized runs, and the first run at any commit is always a full investigation (no prior runs to reuse from), so the loop always has an llm-tp floor to land on — unless every confirmed-unreachable verdict at that commit came from registry rules, in which case null is the correct answer: registry rows must stay live against rule deactivation and are never cached.
