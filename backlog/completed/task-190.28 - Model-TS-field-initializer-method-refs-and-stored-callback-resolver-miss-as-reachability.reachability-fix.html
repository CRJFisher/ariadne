Entry-point classification · TypeScript / JavaScript false positives · shipped

Two TypeScript reads the indexer dropped — and the three captures that restore them

A method stored in a class field (this._proc = this.process) and a function exported through an object shorthand (return { extractValue }) both survived as false-positive entry points — the value-read marking each callable reachable was never captured.

The fix lands entirely in the indexing layer: three tree-sitter capture rules emit the missing read, with no change to detect_indirect_reachability or anything downstream.

The crux in one line

The catch-all read query (identifier) @reference.variable matches only (identifier) nodes. this.process in a field initializer never produced a read of process, and { extractValue } is a (shorthand_property_identifier) node — so the read never existed, and detect_indirect_reachability had nothing to key on. Three new patterns supply exactly those two missing reads.

The AST node-shape gap

Each tree-sitter parse below ends at a leaf the pre-existing read queries could not match (rust). The name needed as a read — process / extractValue — is present in the tree, but reachable only through a node type no query captured.

private _proc = this.process

The pre-existing property-access query required object: (identifier); with object: (this) or (super) it never fired, so process was captured by nothing.

B

object shorthand · not an (identifier), so the catch-all skipped it

A distinct node type. shorthand_property_identifier (object literal) is also distinct from shorthand_property_identifier_pattern (destructuring) — capturing one cannot collide with the other.

Why nothing downstream changed

TASK-348 already widened detect_indirect_reachability: a resolved function or method read as a value (and not at its own definition site) becomes IndirectReachabilityEntry with reason function_reference. The only missing input was the read itself — which these three captures supply.

The three captures that emit the missing read

Case A adds a member-read capture under a class field initializer, narrowed to [(this) (super)] objects. Case B adds a shorthand-property read. TypeScript got both patterns; JavaScript got the shorthand pattern only — three new rules across the two grammars.

The negative guard that keeps Case A narrow

The Case A pattern matches a member_expression initializer only — never a call_expression. A field initialized via a method call, private _result = this.compute(), emits no read of compute.

So an invoked method is never wrongly marked a stored reference; a dedicated test asserts this read set is empty.

Case A — why the resolver finds the method: the scope chain

Once process surfaces as a read inside the class field, detect_indirect_reachability resolves the name to the method symbol. That succeeds because a method name lives in its class body scope, not the method-body scope — its defining_scope_id is the class scope.

A method's defining_scope_id is the class body scope because the method name location sits in the class body, not inside the method. So resolving "process" from the class scope returns the method symbol — exactly the symbol the widened reachability arm marks.

Case B is a same-file reachability approximation — two reads, one acted on

The shipped Case B does not resolve the cross-file destructure. The shorthand-read capture fires where extractValue is defined; that read alone marks the function indirectly reachable. The name extractValue therefore yields two variable reads — and only the second one does the work.

extract.ts · the two reads of extractValue, distinguished by the same-location guard 
function extractValue(s: string) {   // read #1 — function-name (identifier)
  return s.trim();                  //   catch-all fires here, AT the definition site
}
const obj = { extractValue };       // read #2 — shorthand_property_identifier (use site)
Which read marks it reachable

Read #1 is at extractValue's own definition location, so detect_indirect_reachability skips it. Read #2 — the shorthand — is a distinct node at a distinct location, so it marks extractValue reachable.

Full cross-file call resolution for the destructure-then-call path remains separate work.

Net change

Three tree-sitter capture rules (2 in typescript.scm, 1 in javascript.scm) and six tests — zero lines changed in detect_indirect_reachability.

The reachability arm from TASK-348 was already correct; these cases simply never reached it because the read was dropped at the node-type boundary in pass 1.
