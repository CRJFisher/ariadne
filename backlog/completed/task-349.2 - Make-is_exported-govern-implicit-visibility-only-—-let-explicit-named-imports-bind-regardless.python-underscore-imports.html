Nearly every Python row is underscore-prefixed (_make_block, _ensure_sync_result, _parse_mapper_argument, …); one data-completeness defect accounts for the whole Python population.

The crux: the export chain refuses a definition the importer explicitly names

The defining symbol already lives in the DefinitionRegistry at module scope. The chain breaks only because resolve_export_chain reads the is_exported-gated export set, and the underscore name was never admitted to it.

chain breaks at the gate symbol exists at module scope verified: capture_handlers.python.test.ts:1388–1406

The fix: a named-import fallback alongside the submodule fallback

resolve_export_chain stays strictly gated — it is shared by re-export recursion. The new path joins the fallback cascade already sitting at name_resolution.ts:175–184, firing only when the chain returned null and the import is named.

resolve_references/name_resolution.ts — new fallback added BEFORE the submodule fallback (export.ts is NOT touched)
// 162: import_name = original_name || name — original (not alias) for the lookup.
// 166: resolve_export_chain runs first — still gated on is_exported.
resolved = context.exports.resolve_export_chain(source_file, import_name, imp_def.import_kind, …);

// CHANGE B — explicit-named-import fallback, next link in the cascade.
// Runs BEFORE the submodule fallback, so a real module-level definition
// takes precedence over a same-named sibling submodule.
if (!resolved && imp_def.import_kind === "named") {
  const root = context.scopes.get_file_root_scope(source_file);     // module scope ONLY — never nested
  if (root) resolved = context.definitions.get_scope_definitions(root.id)
                       .get(import_name) ?? null;  // miss → stays null (absent name)
}

// then the existing submodule fallback (only reached if still null).
if (!resolved) {
  const submodule_path = context.imports.get_submodule_import_path(imp_def.symbol_id);
  if (submodule_path) resolved = imp_def.symbol_id;
}

// bound under imp_def.name — the ALIAS, not import_name (line 207).
scope_resolutions.set(imp_def.name, resolved);
the mental model

is_exported governs only implicit visibility — the public surface that wildcard, namespace, and re-export resolution read. An explicit named import binds to any module-level definition regardless.

why module scope only — nested defs are also is_exported=false (AC #2, B2)

Nested functions carry is_exported=false too, so a naive "any def by this name" lookup would wrongly bind an explicit import to a nested function. Restricting the lookup to get_file_root_scope(source_file) → get_scope_definitions(root.id) sees only module-level names; nested defs live in different scopes and stay invisible.

Which resolution paths widen, and which keep the gate

Only the named path widens. Everything else keeps reading the is_exported-gated export set, so private names stay off the public surface.

why the re-export row stays unbound

The fallback only finds names physically defined in the resolved source file's module scope. from package import _make_block resolves the source to __init__.py, which does not define _make_block — so the module-scope lookup misses and the private name stays off the package's public surface (B7).

scope boundary — out of this change

The TypeScript rows in this leaf (destructured from the ./_namespaces/ts barrel namespace) fail for an unrelated reason — re-export-chain indirection — and belong to import_resolution (AC #7).

language-agnostic by design — a non-exported TS/JS named import also binds

The fallback keys only on import_kind === "named", so a non-export'd TS/JS or non-pub Rust named import binds too — intended, a strict call-graph improvement. A correctly-exported target is never diverted: resolve_export_chain returns first, so the fallback only runs after a real miss.
