The single mechanism at the heart of the task

detect_indirect_reachability walks every variable_reference read; when the read resolves to a definition it rescues that symbol from the dead-flag set. Today it rescues only kind === "function". Widening that one gate to also accept method is the entire shipped change.

indirect_reachability.ts:85-101 — the gate

A bare read of a bound or instance method (self._acquire_connection, this.write) resolves to a method: definition, but the gate only matches function:, so the method leaks through as a false dead-flag entry point.

Constructor is deliberately excluded — reading a constructor as a value is not a real pattern; constructor invocations arrive as call references, not reads, and the def-site skip at lines 90-96 stays.

The one open scoping decision

Whether to also close the TS field-initializer member-read indexing gap that leaves case 9 (this._processor / Prisma-shaped) unfixed.

Decision · A vs B

Option A — reachability-scoped fix only (recommended). Ship the one-line gate widening + builtin cleanup. Cases 9 & 10 documented as out-of-scope. Smallest surface, honours YAGNI, no capture-handler risk.

Option B — additionally fix the indexing gap. Add an indexing-layer change to capture TS field-init member reads so this.process emits a .process reference reachability can key on. Larger, riskier — touches capture handlers — and only buys case 9.

why case 9 cannot be fixed in reachability

At indexing time a TS field initializer this._processor = this.process captures only a this read; no reference to .process is ever produced for reachability to key on.

Python differs: it decomposes self.process into a bare process read — exactly why case 8, its Python twin, is fixed by this change.
