Self-repair pipeline · plan taxonomy

Naming a permanent limitation, and purging the interim classifier

The plan stage marked classifier-relevant groups with is_classifier_work — framed everywhere as an interim workaround with a durable core fix still pending. But under the registry regime, a classifier has no interim home: the registry holds only permanent limitations, and its builtins are triage's only classifier mechanism.

So the interim-classifier concept was purged from plan, and the flag became is_permanent_limitation: boolean — the one distinction the pipeline actually routes on, threaded from the strategist prompt into the PlanTask.

Why a tri-state was rejected and interim was purged, not renamed

Registry builtins are triage's only classifier mechanism, and the registry (classifier-lifecycle.md) holds only permanent limitations — so an "interim classifier" has nowhere to live. A fixable bug's real deliverable is the core fix in backlog/, not a temporary classifier. The interim concept had no destination, so plan needs exactly one bit: is this fixable, or not?

02The two outcomes land in different places

The flag matters because each value has a distinct destination and owner: a false group is a core-fix task that exports to backlog/ at priority high; a true group routes to classifier-author and becomes a registry entry — it never exports to backlog.

permanent path → registry, never backlog core-fix path → backlog, priority high
The routing that became data-driven

Before, step 3a said the flag "spans two disjoint outcomes" and deferred wholly to a human. Now the skipped_permanent_limitation array from the step-1 dry run is the permanent-limitation worklist: step 2's Kind bullet fetches those rows directly, step 3 dispatches refactor-investigator only for false groups, and step 3a routes the true groups to classifier-author.

The human stays final adjudicator, and the agent gates backstop the call: a fixable bug misrouted to classifier-author hits its "if fixable, stop" gate; a true limitation misrouted to refactor-investigator returns its PERMANENT-LIMITATION verdict.

05Decisions taken — what the design settled on

The pre-build plan floated a tri-state and left one question open; the landed design resolved all of it toward the leanest shape the regime allows.

chosen

A boolean, not a tri-state

is_permanent_limitation: boolean on both StrategistPlanNode and PlanTask. The pipeline routes on exactly one distinction — fixable or not — so a third state would be surface with no consumer.

purged

The interim-classifier concept, entirely

Not renamed — removed. Registry builtins are triage's only classifier mechanism and the registry holds only permanent limitations, so an interim classifier has no home; a fixable bug's deliverable is the core fix.

deleted

The priority machinery

--priority core|classifier, ExportPriority, and derive_backlog_priority/BacklogPriority are gone. With interim purged, every exported row is a core fix at priority: high — no partition to select.

resolved

Permanent rows never export to backlog

The open question is settled: select_exportable_tasks hard-excludes a permanent row in both selection modes into skipped_permanent_limitation — the array prioritize step 3a reads as its worklist.

The one idea to hold

The registry is the permanent-limitations catalog; the backlog is the fixable-bugs queue. Plan now carries one bit — is_permanent_limitation — that maps each group to exactly one of them, with no interim state in between.

The human stays the final adjudicator, but the distinction the pipeline runs on is carried by data end-to-end, and a stale row that lacks the bit fails loudly rather than silently exporting a permanent limitation to backlog/.
